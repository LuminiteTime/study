Итог, у которого нет конца

В уроке 4 задание считало по каждому продавцу накопительный итог через keyBy и reduce. Этот итог растёт с момента запуска и на вопрос «сколько продавец m-0000 принял с 12:00 до 12:01» ответить не может. Антифроду и дашборду нужны итоги за ограниченные отрезки времени. Сколько платежей прошло у продавца за минуту. Сколько раз карта платила подряд без долгих пауз.

У накопительного итога есть и вторая беда. reduce держит по значению на каждый ключ всё время работы задания, и Flink не знает, когда это значение можно выбросить. Окно задаёт обе границы сразу. Оно говорит, когда результат готов к выдаче, и когда его состояние можно удалить.

Квитанция за свет

Представь управляющую компанию. Каждый жилец сдаёт показания счётчика, а бухгалтерия раз в месяц выставляет квитанцию. Месяц здесь это окно, жилец это ключ. Квитанцию за октябрь печатают, когда бухгалтерия решила, что показаний за октябрь больше не будет. Обычно это 3 ноября, к этому дню успевают даже те, кто сдаёт с небольшой задержкой. Такое решение во Flink принимает watermark, ты знаешь его по уроку 5.

Жилец принёс октябрьские показания 10 ноября. Квитанция уже ушла, но перерасчёт разрешён до 25 ноября, и жилец получит исправленную квитанцию. Во Flink это допуск опозданий allowedLateness и позднее срабатывание окна. Показания за октябрь, принесённые в декабре, в октябрь уже не войдут. Их складывают в отдельную папку для ручного разбора, во Flink это побочный выход.

Бухгалтерии незачем хранить каждое показание до конца месяца, ей достаточно текущей суммы по счётчику. Так работает AggregateFunction. А среднее потребление за последние три месяца, которое пересчитывают каждый месяц, это sliding окно. Каждое показание входит в три таких расчёта.

Четыре вида окон

Окно описывается в коде после keyBy вызовом window(...). Аргумент этого вызова называется assigner. Он получает время события записи и возвращает окна, в которые она попадает.

Лента платежей и окна

Обрати внимание на три вещи. В sliding окнах каждый платёж лежит трижды, и счётчик копий в подписи под лентой растёт втрое. Global окно не выдаёт ничего, сколько бы ни шёл watermark. Опоздавший платёж ведёт себя по-разному в зависимости от вида окна и допуска, и в sliding окнах он может попасть только в часть своих окон.

Как tumbling окно находит своё начало

Assigner ничего не ищет в состоянии и не хранит список окон. Начало окна он вычисляет арифметикой от времени записи.

В исходниках

Метод assignWindows у tumbling окна возвращает список из одного окна. Смотри на две детали. Начало берётся из getWindowStartWithOffset, а запись без времени события роняет задание с понятным текстом.

Сама формула занимает три строки. Остаток от деления времени на размер окна отбрасывается, ветка для отрицательного остатка нужна временам до 1970 года.

Проверим на настоящем платеже со стенда. Время события 1794085549065, размер окна 60000 мс, смещение по умолчанию 0. Остаток 49065, значит начало окна 1794085500000, а конец 1794085560000. Ровно такие границы ты увидишь в топике merchant.stats на практике. Окна выровнены по началу эпохи, поэтому минутное окно всегда начинается в ноль секунд по UTC. Сдвинуть границы можно вторым аргументом of(size, offset), это нужно, например, для суточных окон по московскому времени.

Почему sliding окно дорого стоит

В исходниках

У sliding окна тот же метод строит список. Цикл идёт от последнего начала назад с шагом slide, пока окно ещё накрывает запись.

Ёмкость списка задана прямо как size / slide. Окно на 10 минут с шагом в минуту даёт 10 окон на каждую запись, с шагом в 10 секунд уже 60. Документация приводит крайний пример, сутки с шагом в секунду дают 86400 окон на запись.

Документация: Useful state size considerations

Как сессии склеиваются

Сессионное окно заранее не знает своих границ. Поэтому каждая запись сначала получает собственное окно длиной в паузу, а потом оператор склеивает его с соседними.

В исходниках

Assigner сессий возвращает окно от времени записи до этого времени плюс пауза.

Склеиваются окна, которые пересекаются или касаются друг друга. Результат накрывает оба окна.

При склейке накопленные значения двух окон объединяются. Для состояния в куче это вызов merge твоей AggregateFunction. Метод выше, add, показывает, что состояние адресуется текущим namespace, то есть окном.

Отсюда правило. Метод merge в AggregateFunction вызывается только при склейке окон. Tumbling окна его не трогают. Сессии без него дадут неверный результат. Конец сессии всегда равен времени последнего платежа плюс пауза.

Документация: Session Windows

Global окно устроено проще всех. Все записи ключа попадают в одно окно, а trigger по умолчанию у него никогда не срабатывает.

В исходниках

Фабрика create подставляет NeverTrigger, комментарий прямо предупреждает, что без своего trigger вычислений не будет.

Конец global окна равен Long.MAX_VALUE, поэтому оно никогда не считается опоздавшим и само из состояния не удаляется. Global окно имеет смысл только вместе со своим trigger и логикой очистки.

Документация: Global Windows

Из чего собран оконный оператор

За вызовами window(...) и aggregate(...) стоит один оператор WindowOperator из четырёх частей.

  • Assigner решает, в какие окна попадает запись. Мы его только что разобрали.
  • Trigger решает, когда окно готово отдать результат и нужно ли после этого очистить его содержимое. У каждого assigner есть trigger по умолчанию.
  • Evictor может выкинуть часть записей из окна до или после вызова функции. Он необязателен и дорого обходится, об этом ниже.
  • Функция окна считает результат. Это ReduceFunction, AggregateFunction или ProcessWindowFunction.

В исходниках

Вот путь одной записи через оператор для окон без склейки. Assigner вызывается в начале processElement, дальше цикл по окнам записи.

Для каждого окна выполняются одни и те же шаги. Опоздавшее окно пропускается. Состояние переключается на namespace этого окна, и запись добавляется туда. Trigger получает запись и отвечает FIRE, PURGE, оба сразу или ничего. На каждое окно регистрируется таймер очистки. Отсюда видно, как окно живёт в состоянии. Это обычный keyed state, где к ключу добавлен namespace окна, поэтому у одного продавца одновременно может жить несколько окон.

Документация: Window Lifecycle

Когда окно срабатывает

В исходниках

Trigger по умолчанию для окон по времени события называется EventTimeTrigger. Посмотри, что он делает на каждую запись и на таймер.

Если watermark ещё не дошёл до окна, trigger ставит таймер на maxTimestamp окна. Таймер по времени события срабатывает, когда watermark его догоняет. Если watermark уже позади окна, trigger срабатывает сразу, на этой самой записи. Это и есть позднее срабатывание. maxTimestamp на единицу меньше конца, потому что конец окна в него не входит.

Для нашего минутного окна, которое заканчивается в 1794085560000, таймер стоит на 1794085559999. Итог уйдёт, как только watermark станет не меньше этого числа. При задержке watermark в 10 с из урока 5 это случится, когда задание увидит платёж с временем около 12:01:10.

Документация: Triggers

AggregateFunction или ProcessWindowFunction

ProcessWindowFunction получает все записи окна разом и вдобавок контекст с границами окна. AggregateFunction видит записи по одной, складывает их в аккумулятор и о границах окна ничего не знает. Разница в стоимости решается в момент построения оператора.

В исходниках

Вызов aggregate с двумя функциями строит состояние типа AggregatingStateDescriptor. В нём лежит один аккумулятор на окно.

Вызов process с одной ProcessWindowFunction строит ListStateDescriptor. Это список всех записей окна.

Обрати внимание на ветку evictor != null в обоих методах. С evictor даже aggregate собирает оператор, который хранит все записи, потому что evictor должен их видеть. Предварительное сложение пропадает.

Документация: ProcessWindowFunction with Incremental Aggregation, Evictors

Посчитаем для PayGuard. Примерно 200 платежей в секунду, окно в минуту, значит около 12000 платежей в окне на всех продавцов. С ProcessWindowFunction все они лежат в состоянии до конца окна и ещё минуту допуска. С AggregateFunction в состоянии 50 аккумуляторов по два числа. Две функции можно соединить. Аккумулятор копится по мере прихода записей, а ProcessWindowFunction в конце получает один готовый результат и добавляет к нему границы окна. Так сделан наш MerchantStatsWindow.

Опоздавшие платежи

У watermark есть задержка, но часть платежей приходит ещё позже. По умолчанию допуск опозданий равен нулю, и такая запись молча отбрасывается. Метрика numLateRecordsDropped на операторе увеличится на единицу, и больше ты ничего не узнаешь. Два вызова меняют это поведение. allowedLateness держит окно в состоянии дольше, и опоздавшая запись вызывает пересчёт. sideOutputLateData отправляет записи, которые не принял уже никто, в побочный выход.

В исходниках

Окно считается опоздавшим, когда watermark дошёл до его времени очистки. Время очистки равно maxTimestamp плюс допуск.

В конце processElement запись уходит в побочный выход, только если её не приняло ни одно окно. Без тега она просто считается в метрике.

Отсюда тонкость с sliding окнами, которую видно в визуализации. Опоздавший платёж может не попасть в старые окна и при этом попасть в одно ещё живое. Тогда в побочный выход он не уйдёт. Старые окна так и останутся без него.

Документация: Allowed Lateness, Side Outputs

⚠
Одно окно, несколько итогов

При допуске больше нуля каждое позднее срабатывание выдаёт итог окна заново, уже с опоздавшим платежом. В топике merchant.stats окажется несколько записей с одним продавцом и одним windowStartMs. Последняя из них верная. Потребитель должен перезаписывать итог по ключу из продавца и начала окна, то есть делать upsert. Простое сложение всех записей подряд даст завышенный оборот.

Сравнение со Spark

В Spark Structured Streaming окно задаётся функцией window(col, "1 minute") внутри groupBy, для скользящего окна передаётся третий аргумент с шагом, для сессий есть session_window. Порог опоздания там один, это задержка из withWatermark. Она же определяет, когда окно выдаёт итог в режиме append и когда его состояние выбрасывается. Записи позже этого порога Spark вправе отбросить, и побочного выхода для них нет.

Во Flink это три независимые настройки. Задержка watermark решает, когда окно сработает впервые. allowedLateness решает, сколько ещё окно ждёт опоздавших. Побочный выход ловит то, что не дождалось. Сверх этого во Flink можно заменить trigger и выдавать, например, промежуточный итог каждые 10 секунд, не дожидаясь конца окна.
