Класс целиком.

Решения внутри класса.

  • Соль равна Math.floorMod(paymentId.hashCode(), salts). Идентификатор платежа случаен, поэтому части получаются почти равными, а одинаковый платёж всегда даёт одинаковый ключ. floorMod нужен, потому что hashCode бывает отрицательным.
  • Первая фаза использует тот же PaymentTotals, что и старое окно. Сумма и количество складываются, поэтому частичный итог совместим со второй фазой. PartialStats отрезает соль от ключа и кладёт в MerchantStats настоящего продавца с границами окна.
  • Вторая фаза это reduce по продавцу в таком же минутном окне. Она хранит один объект на ключ и окно и складывает части по мере прихода.
  • В первой фазе нет allowedLateness. Окно с допуском опозданий выпускает итог повторно на каждый опоздавший платёж, и вторая фаза сложила бы обновлённый частичный итог с прежним. Опоздавшие платежи уходят в боковой выход и дальше в payments.late.

Почему вторая фаза попадает в нужное окно. Её записи несут время события, которое им назначило окно первой фазы.

В исходниках

Перед вызовом функции окна оператор ставит всем её выходным записям одно время, максимум окна.

Максимум окна на единицу меньше его конца.

Для окна с 12:00 до 12:01 частичные итоги получат время 12:00:59.999 и попадут во второй фазе в то же окно. Сработает оно, когда watermark пройдёт конец минуты, то есть сразу после первой фазы.

Документация: Windows

Поле и чтение флага в JobConfig.

Подключение в PayGuardJob. Боковой выход опоздавших берётся у первой фазы, потому что именно она стоит на сыром потоке платежей. При выключенной соли firstStats это старое окно, и поведение не меняется.

Тест. MiniCluster из урока 16, параллелизм 4, соль 8. Платежи с временем 1000-1099 мс попадают в первую минуту, и после двух фаз ожидается одна строка.

Запуск на стенде. Сначала без соли, потом с солью, каждый раз отменяя предыдущее задание.

./gradlew test --tests '*SaltedMerchantStatsTest' shadowJar
docker compose exec -T jobmanager flink run --detached -p 4 /jobs/payguard-1.0.0.jar
scripts/vertex-load.sh

docker compose exec -T jobmanager flink cancel "$JOB"
docker compose exec -T jobmanager flink run --detached -p 4 /jobs/payguard-1.0.0.jar --stats-salts 16
scripts/vertex-load.sh

Перед отменой получи $JOB той же командой, что в практике. Цифры на стенде при 200 платежах в секунду.

Почему разброс не стал единицей. С солью 16 продавец m-0000 превратился в 16 ключей примерно по 1,9 % потока. Обычный продавец получает 70 % на 49 продавцов, около 1,4 %. Горячего ключа больше нет, а остаток неравномерности даёт раскладка 800 ключей по группам ключей и подзадачам, её ты видел в уроке 4.

Корректность проверь в Postgres. Возьми одну законченную минуту и сравни строку m-0000 с суммой по всем продавцам.

docker compose exec -T postgres psql -U payguard -d payguard -c \
  "select merchant_id, payment_count from merchant_stats
   where window_start_ms = (select max(window_start_ms) - 60000 from merchant_stats)
   order by payment_count desc limit 3"

У нас за минуту на m-0000 пришлось 3285 платежей из 10969, это 30 %, ровно столько задано в PaymentFactory. Соль поменяла раскладку работы и не тронула результат.
