Что будет в конце

Ты встроишь в задание учебный тормоз и включишь его флагом. На стенде увидишь, как одна медленная вершина раскрашивает весь граф, найдёшь её скриптом по REST, снимешь flame graph и сравнишь три режима чекпоинтов. Цифры в тексте получены на стенде курса при 200 платежах в секунду и параллелизме 2.

Файлы задания, это класс SaltedMerchantStats и его тест, пока не создавай. В снапшоте solutions/lesson-18 они уже есть, и строки 92-104 в PayGuardJob тоже относятся к заданию.

Шаг 1. Учебный тормоз

Создай src/main/java/dev/study/payguard/pipeline/SlowDown.java. Он изображает приёмник, который на каждую запись ходит во внешнюю систему и ждёт ответа.

ПРОСТЫМИ СЛОВАМИ

Обычный map, который возвращает запись без изменений. Он нужен только ради паузы.

При нулевой задержке оператор ничего не делает, поэтому его можно оставить в графе навсегда и включать флагом.

Thread.sleep держит поток задачи. Для Flink это время работы оператора, и оно попадёт в busy. Процессор при этом свободен.

Запись уходит дальше, к приёмнику Kafka.

Задержку берём из аргументов. В record JobConfig добавь поле.

И его чтение в fromArgs на той же позиции. По умолчанию тормоз выключен.

Встрой оператор после card-profile. Вызов returns нужен, потому что SlowDown обобщённый, и без подсказки Java сотрёт тип записи. Запрет обобщённых типов из урока 3 тогда уронит задание при сборке графа.

Между card-profile и slow-down нет смены ключа и параллелизма, поэтому Flink сцепит их в одну вершину. В интерфейсе она будет называться card-profile -> slow-down.

Шаг 2. Flame graph и переключатель debloat в Compose

В docker-compose.yml появились две строки в общих настройках Flink.

rest.flamegraph.enabled включает вкладку Flame Graph в Web UI и REST-ручку под ней. На проде документация советует считать её экспериментальной.

Во второй строке значение берётся из переменной окружения. Запись ${BUFFER_DEBLOAT:-false} Docker Compose раскрывает сам. Если переменная BUFFER_DEBLOAT не задана, подставится false. Так один файл обслуживает оба опыта.

Шаг 3. Скрипт нагрузки по вершинам

Смотреть каждую вершину в интерфейсе долго. Создай scripts/vertex-load.sh, он печатает одну строку на вершину.

ПРОСТЫМИ СЛОВАМИ

Берём из описания задания пары «идентификатор вершины и имя». Цикл while read разбирает их по одной.

Ручка subtasks/metrics сразу агрегирует метрику по всем подзадачам вершины и отдаёт min, max, avg и sum. Мы просим три метрики.

Ответ это массив объектов с полем id. Выражение jq превращает его в словарь по имени метрики, чтобы обращаться к полям по имени.

Для busy и back берём максимум по подзадачам, как это делает граф в Web UI. Для numRecordsIn берём минимум и максимум, их отношение показывает перекос. Запись // 0 подставляет ноль, если метрики у вершины нет.

read -r с подстановкой процесса кладёт четыре числа в переменные, а printf печатает строку таблицы. Шаблон %-46.46s выравнивает имя по левому краю и обрезает его до 46 символов.

Сделай скрипт исполняемым командой chmod +x scripts/vertex-load.sh. Метрика numRecordsIn накопительная, она растёт с запуска подзадачи. Сравнивай минимум и максимум внутри одного вызова, между вызовами они разные.

Шаг 5. Включи тормоз

Отмени задание и отправь его заново с задержкой 20 мс. Состояние для опыта не нужно. Смещения Kafka группа payguard хранит сама, поэтому новое задание продолжит с места, где остановилось старое.

JOB=$(curl -s localhost:8081/jobs | jq -r '[.jobs[] | select(.status == "RUNNING")][0].id')
docker compose exec -T jobmanager flink cancel "$JOB"
scripts/submit.sh --slow-ms 20

Первая строка достаёт идентификатор запущенного задания из REST, так же как это делают наши скрипты. Аргумент --slow-ms 20 скрипт submit.sh передаёт заданию, его прочитает JobConfig.

Посчитай заранее. На подзадачу card-profile -> slow-down приходится около 100 записей в секунду, а по 20 мс на запись она успевает не больше 50. Через минуту снова запусти scripts/vertex-load.sh. Вот что получилось у нас.

Шаг 6. Спроси REST про backpressure

Вкладка Back Pressure в Web UI берёт данные из ручки /backpressure. Её удобно звать из скрипта.

JOB=$(curl -s localhost:8081/jobs | jq -r '[.jobs[] | select(.status == "RUNNING")][0].id')
VERTEX=$(curl -s localhost:8081/jobs/$JOB | jq -r '.vertices[] | select(.name | contains("deduplicate")) | .id')
curl -s localhost:8081/jobs/$JOB/vertices/$VERTEX/backpressure \
  | jq '{level: .backpressureLevel, subtasks: [.subtasks[] | {subtask, ratio, busyRatio}]}'

Вторая строка находит идентификатор вершины по части имени. Последняя оставляет из ответа уровень вершины и по каждой подзадаче долю backpressure и долю занятости. У нас ручка вернула уровень high и долю 0.999. Это те же 999 мс из таблицы выше, делённые на 1000. Если запросить ту же ручку для slow-down, уровень будет ok, потому что узкое место само никого не ждёт.

Шаг 7. Flame graph

Открой http://localhost:8081, зайди в задание и кликни по вершине card-profile -> slow-down. Справа появится вкладка Flame Graph с переключателем On-CPU, Off-CPU и Mixed. То же можно получить через REST.

VERTEX=$(curl -s localhost:8081/jobs/$JOB | jq -r '.vertices[] | select(.name | contains("slow-down")) | .id')
curl -s "localhost:8081/jobs/$JOB/vertices/$VERTEX/flamegraph?type=full" | jq '{endTimestamp, samples: .data.value}'

Параметр type принимает full, on_cpu и off_cpu. Первый запрос только запускает сбор снимков, и в ответе будет endTimestamp равный -3 без данных. Так VertexFlameGraph.waiting() помечает граф, который ещё строится. Повтори запрос через несколько секунд.

У нас полный граф собрал 200 снимков. Это совпадает с умолчанием в 100 снимков, сложенных по двум подзадачам. Самая толстая стопка шла по цепочке StreamTask.runMailboxLoop, processInput, emitNext. Это главный цикл подзадачи из урока 1, который читает запись и проталкивает её по цепочке операторов. Выше по стопке, в вызовах операторов цепочки, ищи SlowDown.map и Thread.sleep. В режиме on_cpu этот кусок исчезнет, потому что спящий поток находится в состоянии TIMED_WAITING.

В интерфейсе граф читается снизу вверх. Нижняя полоса это корень, над ней методы, которые он вызвал. Ширина полосы это доля снимков, а цвет ничего не значит. Наведи курсор на полосу, и интерфейс покажет полное имя метода с номером строки.

Шаг 8. Unaligned-чекпоинты под той же нагрузкой

Перезапусти задание с включёнными unaligned-чекпоинтами. Настройку можно передать прямо в flink run, не трогая Compose.

JOB=$(curl -s localhost:8081/jobs | jq -r '[.jobs[] | select(.status == "RUNNING")][0].id')
docker compose exec -T jobmanager flink cancel "$JOB"
docker compose exec -T jobmanager flink run --detached \
  -Dexecution.checkpointing.unaligned.enabled=true \
  /jobs/payguard-1.0.0.jar --slow-ms 20

Флаг -D задаёт настройку только этому заданию. Он должен стоять до пути к jar, иначе CLI примет его за аргумент программы. По этой же причине мы не используем здесь submit.sh.

Чекпоинты стали 129-293 мс, в каждом записано 705-1011 КиБ данных в полёте. Эти байты барьер обогнал и сохранил. В Web UI на вкладке Checkpoints колонка Processed (persisted) in-flight data показывает их по каждой подзадаче. Лаг при этом был 10760 и продолжал расти.

Шаг 9. Buffer debloating

Вернись к выровненным чекпоинтам и включи debloat через переменную из шага 2. Compose увидит изменившуюся настройку и пересоздаст контейнеры JobManager и TaskManager. Кластер без высокой доступности при этом теряет запущенное задание, поэтому его надо отправить снова.

BUFFER_DEBLOAT=true docker compose up -d --wait
scripts/submit.sh --slow-ms 20

Чекпоинты пошли за 1540-2368 мс, через барьер проходит 29-54 КиБ данных. Это примерно столько, сколько медленная подзадача разбирает за целевую секунду. Без debloat в той же очереди стояли буферы полного размера, по умолчанию 32 КиБ, и выравнивание занимало десятки секунд. Лаг дошёл до 16421 и тоже рос.

Закончи опыт. Отмени задание, верни Compose к обычным настройкам командой docker compose up -d --wait без переменной и отправь задание без тормоза через scripts/submit.sh.

Как это выглядит в проде

Порядок разбора всегда один. Алерт на backpressure или лаг, потом граф с busy и back от источника вниз, потом flame graph узкой вершины, потом решение по причине. Режим чекпоинтов выбирают заранее, чтобы пробка не превращалась ещё и в долгое восстановление.
