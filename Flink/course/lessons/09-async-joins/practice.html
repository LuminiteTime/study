Что будет в конце

В стенде появится PostgreSQL со справочником продавцов. Каждый алерт перед отправкой в fraud.alerts получит поле merchantRisk из базы через асинхронный оператор с кэшем. Генератор начнёт присылать подтверждения от банка в топик payments.confirmations, а задание будет соединять их с платежами и писать пары в payments.confirmed.

Правило «подтверждение не пришло» относится к заданию. Файлы UnconfirmedPaymentFunction и его тест пока не создавай.

Шаг 1. PostgreSQL в Compose

Добавь в docker-compose.yml службу базы, переменные подключения и два новых топика.

Переменные PAYGUARD_DB_* добавлены в общий блок Flink. Их прочитает TaskManager, потому что соединение с базой открывается там, где работает подзадача. Образ PostgreSQL выполняет скрипты из /docker-entrypoint-initdb.d, когда каталог данных пуст. Том для данных базы мы не монтируем, поэтому после docker compose down справочник создаётся заново. Проверка healthcheck вызывает pg_isready, и флаг --wait дождётся, пока база начнёт принимать соединения.

Сам скрипт создаёт таблицу и 50 продавцов. Уровень риска считается от номера продавца. Каждый десятый получает HIGH, каждый третий из оставшихся MEDIUM, остальные LOW.

Шаг 2. Зависимости

Драйвера PostgreSQL и пула соединений HikariCP в образе Flink нет, поэтому обе библиотеки идут через implementation и попадают в толстый jar. Пул нужен, чтобы восемь потоков обогащения не открывали соединение на каждый запрос.

Шаг 3. Модели и настройки

Алерт получает поле риска. Пока алерт не прошёл обогащение, в поле стоит NOT_LOADED. Значение UNKNOWN означает, что база не ответила или продавца в ней нет. Отдельные значения помогут отличить в топике сбой обогащения от алерта, который его не проходил.

Подтверждение банка и результат соединения это два новых record.

В настройки задания добавь имена двух топиков.

Шаг 4. Справочник продавцов

Обогащение не должно знать про JDBC. Интерфейс MerchantDirectory позволяет тесту подставить справочник, который отвечает мгновенно, падает или зависает.

Реализация на JDBC берёт адрес и пароль из переменных окружения. Соединения пула открываются только для чтения, размер пула передаётся снаружи.

Шаг 5. Асинхронное обогащение

Создай pipeline/AlertEnrichment.java.

Обрати внимание на конструктор. Функция пересылается на кластер в сериализованном виде, а HikariDataSource сериализовать нельзя. Поэтому в поле лежит SerializableSupplier, и сам справочник создаётся в open, уже в TaskManager. Все поля, которые создаются в open, помечены transient. С ошибкой is not serializable ты встречался в уроке 8, здесь её избегаем заранее.

ПРОСТЫМИ СЛОВАМИ

asyncInvoke вызывается в потоке подзадачи на каждый алерт. Он должен вернуться быстро.

Сначала смотрим в кэш. Если риск продавца есть и ещё свежий, сразу завершаем запись готовым алертом. В базу не ходим.

Иначе отдаём запрос пулу из восьми потоков через supplyAsync и выходим из метода. Поток подзадачи свободен для следующей записи.

Когда пул получит ответ, whenComplete завершит запись. При ошибке базы вместо риска будет UNKNOWN, и счётчик merchantLookupFailures вырастет на единицу. Задание не упадёт.

timeout вызывается, если за 2 секунды ответа нет. Выдаём алерт с UNKNOWN вместо исключения, которое перезапустило бы задание.

Метод complete может вызваться дважды, если ответ базы пришёл одновременно с timeout. Оператор защищён от этого флагом completed в своём обработчике результата, второй вызов игнорируется.

Шаг 6. Подтверждения в генераторе

Генератор теперь для каждого платежа решает, пришлёт ли банк подтверждение. По умолчанию подтверждается 95 % платежей. Время подтверждения отстоит от времени платежа на случайную величину до трёх секунд.

Флаг --confirm задаёт долю подтверждённых платежей. С --confirm 0.5 половина платежей останется без пары, это пригодится в задании.

Шаг 7. Interval join

Создай pipeline/PaymentConfirmationJoin.java.

ПРОСТЫМИ СЛОВАМИ

Метод принимает два потока и возвращает поток пар. Так он подключается в задании одной строкой и проверяется в тесте отдельно.

Обе стороны разбиты по paymentId. Interval join работает только на двух потоках с ключом, и ключи должны совпадать по типу.

between(Duration.ZERO, MAX_DELAY) означает, что подтверждение должно иметь время от момента платежа до пяти минут после него. Обе границы включены.

ProcessJoinFunction вызывается на каждую найденную пару и строит ConfirmedPayment с задержкой подтверждения.

Имя и uid вершины. uid понадобится, когда состояние соединения будет восстанавливаться из savepoint.

Шаг 8. Подключи всё в задании

В PayGuardJob появляются три константы обогащения. Размер пула соединений совпадает с числом потоков в AlertEnrichment, лишние соединения простаивали бы.

Источник подтверждений и стратегия watermark для него. Подтверждения не проходят разбор с DLQ, поэтому для них подходит LenientJsonSchema из урока 8. Допуск беспорядка и idleness взяты из PaymentWatermarks, чтобы оба входа соединения понимали время одинаково.

Соединение подключается к тому же потоку payments после дедупликации, что и окна. Поток подтверждений создаётся в main, его же возьмёт правило из задания.

Алерты обоих правил объединяются и проходят через асинхронный оператор перед приёмником. Объединение возвращает fraudAlerts, и в снапшоте оно уже содержит третий поток из задания. В практике метод вернёт только dynamicAlerts.union(amountAlerts). Асинхронный оператор встаёт в sinkAlerts перед приёмником.

Лямбда в конструкторе AlertEnrichment имеет тип SerializableSupplier, поэтому Java сделает её сериализуемой. Внутри она ссылается только на статическую константу, и вместе с функцией на кластер не уедет ничего лишнего. Не забудь импорты AsyncDataStream, TimeUnit, Duration и WatermarkStrategy.

Шаг 9. Тесты

Тест обогащения запускает настоящий асинхронный оператор на MiniCluster с тремя справочниками. Первый отвечает сразу, второй всегда бросает исключение, третий засыпает на минуту. Третий случай с timeout 200 мс проверяет, что зависшая база даёт UNKNOWN и задание при этом не падает.

Тест соединения проверяет границы интервала. Подтверждение p1 пришло через 2 секунды и соединяется. Подтверждение p2 пришло через 998 секунд, это больше пяти минут, и пары нет.
