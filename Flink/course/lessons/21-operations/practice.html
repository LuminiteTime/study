Что будет в конце

Стенд из Compose проходит итоговый хаос-тест без дублей в fraud.alerts. Тот же стенд с надстройкой SASL пускает к брокеру только клиентов с паролем, и PayGuard вместе с генератором работают через неё. В репозитории появляется сценарий выпуска образа. Файлы ops/runbook.md и ops/production-readiness.md из снапшота относятся к заданию, пока их создавать не нужно.

Шаг 1. Учётные данные Kafka из окружения

Создай src/main/java/dev/study/payguard/job/KafkaSecurity.java. Класс собирает свойства подключения к Kafka для всех клиентов проекта, источников, приёмников и генератора.

ПРОСТЫМИ СЛОВАМИ

Метод всегда возвращает новый объект Properties, поэтому вызывающий код может спокойно дописывать в него свои ключи.

Если переменной PAYGUARD_KAFKA_USER нет, свойства пустые, и клиент подключается без аутентификации. Так старый стенд и тесты работают без изменений.

Протокол SASL_PLAINTEXT включает аутентификацию без шифрования. Комментарий напоминает, что в проде здесь стоит SASL_SSL.

Механизм PLAIN передаёт логин и пароль как есть, брокер сверяет их со своим списком.

Строка JAAS называет модуль входа клиента Kafka и передаёт ему логин и пароль из окружения. Кавычки вокруг значений и точка с запятой в конце обязательны по синтаксису JAAS.

Шаг 2. Подключи свойства ко всем клиентам

В KafkaSinks приёмник at-least-once получает свойства через setKafkaProducerConfig. В exactly-once приёмнике объект из fromEnvironment становится основой, и в него дописывается тайм-аут транзакции из урока 12.

Все три источника в PayGuardJob получают те же свойства через setProperties. Метод копирует ключи в общий набор свойств источника, поэтому порядок вызовов в строителе не важен.

Генератор живёт в том же jar и берёт класс из пакета задания.

Пока переменные окружения не заданы, поведение проекта не меняется. Это пригодится в шаге 4, где хаос-тест идёт на обычном стенде без паролей.

Шаг 3. Надстройка Compose с SASL

Положи рядом с docker-compose.yml файл docker-compose.sasl.yml. Это надстройка (override file). Compose читает основной файл, потом надстройку и сливает их. Словари вроде environment объединяются по ключам, а списки вроде command заменяются целиком.

Разберём по блокам.

  • Якорь x-flink-kafka-auth задаёт переменные для JobManager и TaskManager. Их читает KafkaSecurity. Пароль подставляется из файла .env.
  • KAFKA_LISTENER_SECURITY_PROTOCOL_MAP переводит слушатели INTERNAL и EXTERNAL на SASL_PLAINTEXT. Слушатель CONTROLLER для внутреннего кворума KRaft остаётся без пароля.
  • Две строки JAAS задают серверную сторону PLAIN для каждого слушателя. Пары user_admin и user_payguard объявляют учётные записи брокера и их пароли, а username и password брокер использует сам для связи между брокерами.
  • Проверка здоровья и kafka-init теперь ходят с учёткой admin. Скрипт пишет файл client.properties и передаёт его через --command-config. Двойной $$ нужен, чтобы Compose не подставил переменную сам и оставил её оболочке контейнера.

Команда kafka-init в надстройке заменяет исходную целиком, поэтому в ней повторён весь список топиков вместе с компактируемым merchants.changelog из урока 15. Забыть один топик при таком копировании легко, первая версия надстройки так и потеряла merchants.changelog. SQL-кластер в режиме SASL мы не запускали.

Пароли лежат в .env.example. Это образец, настоящий .env создаётся копией и в git не попадает.

Шаг 4. Итоговый хаос-тест

Создай scripts/final-chaos.sh. Он по очереди ломает три компонента стенда и в конце проверяет дубли.

ПРОСТЫМИ СЛОВАМИ

Функция step печатает заголовок шага, выполняет переданную команду, ждёт PAUSE секунд и печатает первую строку отчёта о чекпоинтах из урока 11. В ней три счётчика, завершённые, неудачные и восстановления.

Первый шаг вызывает chaos-kill-tm.sh из урока 11. Тот убивает TaskManager сигналом SIGKILL и ждёт, пока задание восстановится из чекпоинта.

Второй шаг останавливает PostgreSQL на 30 секунд и запускает обратно. Вывод Compose уходит в /dev/null, чтобы не мешать отчёту.

Третий шаг перезапускает контейнер Kafka. Задание должно переподключиться без рестарта.

В конце verify-no-duplicates.sh из урока 12 читает fraud.alerts с read_committed и считает идентификаторы алертов, встретившиеся дважды.

Собери проект и подними обычный стенд. Переменная COMPOSE_FILE в этот момент не должна быть задана.

./gradlew shadowJar
docker compose up -d --wait
./scripts/submit.sh
./gradlew loadgen --args="--rate 200 --dup 0.02"

Генератор пишет 200 платежей в секунду и дублирует 2 % из них, чтобы дедупликация из урока 7 тоже работала под нагрузкой. Во втором терминале дай заданию сделать несколько чекпоинтов и запусти тест.

PAUSE=45 ./scripts/final-chaos.sh

Переменная PAUSE задаёт паузу после каждого шага. 45 секунд хватает на три чекпоинта при интервале 15 секунд. Итог нашего прогона сведён в таблицу, это первая строка отчёта после каждого шага.

Последняя строка вывода скрипта.

fraud.alerts [read_committed]: записей 7, идентификаторов с повтором 0

Для сравнения запусти проверку с уровнем изоляции read_uncommitted.

./scripts/verify-no-duplicates.sh fraud.alerts alertId read_uncommitted
fraud.alerts [read_uncommitted]: записей 12, идентификаторов с повтором 2

Лишние пять записей и два повтора это данные транзакций, которые отменились при восстановлениях. Потребитель read_committed их не видит, так и работает exactly-once из урока 12.

Теперь посмотри, что задание пережило. История исключений доступна через REST.

JOB=$(curl -s localhost:8081/jobs | jq -r '[.jobs[] | select(.status == "RUNNING")][0].id')
curl -s localhost:8081/jobs/$JOB/exceptions | jq -r '.exceptionHistory.entries[].exceptionName'

Первая команда находит идентификатор запущенного задания, вторая печатает имена исключений из истории. У нас там было пять записей. Три раза java.io.IOException: unable to open JDBC writer, это рестарты без базы, каждый падал на открытии JDBC-приёмника, а exponential-delay растягивал паузы между ними. Ещё FlinkExpectedException: The TaskExecutor is shutting down. и ResourceManagerException: TaskManager with id 192.168.97.5:38213-1d33ea is no longer reachable., это следы убитого TaskManager. Задание в конце RUNNING.

Такая история и есть материал для runbook. Каждое исключение здесь ожидаемое, и дежурный должен уметь отличить его от исключения из аварии в теории.

Шаг 5. Стенд с SASL

Останови обычный стенд и включи надстройку.

docker compose down
cp .env.example .env
export COMPOSE_FILE=docker-compose.yml:docker-compose.sasl.yml
docker compose up -d --wait

cp создаёт рабочий .env из образца, Compose читает его автоматически из папки проекта. Переменная COMPOSE_FILE перечисляет файлы через двоеточие и действует как пара флагов -f. Мы выбрали её по двум причинам. Все скрипты в scripts/ вызывают docker compose без флагов и тоже подхватят надстройку. Сохранить строку с двумя -f в переменной и раскрыть её как команду в zsh не получится, zsh не делит значение переменной на слова. В нашем прогоне брокер стал healthy через 6 секунд, kafka-init создал топики с учёткой admin.

Проверь, что анонимный клиент больше не проходит.

timeout 30 docker compose exec -T kafka /opt/kafka/bin/kafka-topics.sh --bootstrap-server localhost:9092 --list; echo $?

Команда без --command-config не получает ответа и висит до таймаута. timeout обрывает её и возвращает код 124, его печатает echo $?. Причина видна в логе брокера, docker compose logs kafka.

WARN ... Unexpected error from /127.0.0.1 ...; closing connection
org.apache.kafka.common.errors.InvalidRequestException: Unexpected Kafka request of type METADATA during SASL handshake.

Клиент сразу отправил запрос метаданных, а брокер на этом слушателе ждал рукопожатие SASL. Он закрыл соединение, клиент переподключался и повторял то же самое.

Запусти задание и генератор с учётными данными.

./scripts/submit.sh
PAYGUARD_KAFKA_USER=payguard PAYGUARD_KAFKA_PASSWORD=payguard-secret ./gradlew loadgen --args="--rate 200"

Заданию переменные передавать не нужно. flink run выполняется внутри контейнера JobManager, а надстройка уже положила туда PAYGUARD_KAFKA_USER и пароль. Генератор работает на твоей машине, поэтому переменные заданы прямо перед командой и действуют только на неё. Через 90 секунд проверь чекпоинты.

./scripts/checkpoint-report.sh | head -1
Завершено: 7 неудачных: 0 восстановлений: 0

Исключений в истории ноль, задание RUNNING. В Web UI источник payments-raw прочитал 17240 записей, payment-confirmations 16400. Значит, оба потока идут через SASL. Файл .env должен появиться до up. Без него Compose подставит вместо паролей пустые строки и предупредит об этом при старте.

Вернуть обычный стенд можно так.

docker compose down
unset COMPOSE_FILE

Шаг 6. Выпуск образа

Создай .github/workflows/release.yml.

Сценарий запускается только на push тега, который начинается с v. Права packages: write разрешают встроенному токену GITHUB_TOKEN писать в реестр, а contents: read оставляет репозиторий только для чтения. Шаг Gradle гоняет быстрые тесты, сквозные тесты на Testcontainers из урока 16 и собирает толстый jar. Отличие от ci.yml в том, что всё делается в одном задании, и образ строится только после зелёных тестов. Имя образа собирается из имени репозитория, а тег из github.ref_name, то есть из имени тега git. Выпуск запускается так.

git tag v1.0.0
git push origin v1.0.0

Этот сценарий мы на GitHub не запускали. Он лежит в снапшоте как образец, проверь его на своём репозитории. В k8s/payguard.yaml после этого в поле image пишется полное имя образа из ghcr.io, а для приватного пакета кластеру понадобится секрет для доступа к реестру.

Шаг 7. Если цикл уже начался

Повтори порядок действий из теории на Kubernetes-стенде урока 20. Вывод этих команд мы не сохраняли, поэтому здесь только последовательность. Сначала убедись, что у Kafka есть том, иначе цикл повторится при следующем рестарте брокера.

kubectl get pvc kafka-data
kubectl apply -f k8s/infra.yaml
kubectl delete flinkdep payguard
kubectl get configmap
kubectl delete configmap payguard-cluster-config-map payguard-<jobId>-config-map
kubectl apply -f k8s/payguard.yaml

kubectl get configmap покажет ConfigMap кластера, в уроке 20 их было пять. Удалять нужно две с метаданными HA, payguard-cluster-config-map и payguard-<jobId>-config-map с идентификатором задания из списка. Остальные оператор создаст заново. После apply задание стартует без состояния.

Если хочешь сохранить состояние карт, есть аккуратный путь из теории, который мы не проверяли. Меняется uid приёмника алертов вот в этом месте PayGuardJob.

После выпуска образа с новым uid в спецификации задания задаются initialSavepointPath с путём к последнему сохранённому снимку и allowNonRestoredState: true. Прогони это сначала на копии стенда.
