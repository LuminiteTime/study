Что будет в конце

Стенд показывает, на какие области Flink разбил память TaskManager, и ты сверишь их с калькулятором. RocksDB отдаёт в Prometheus метрики своего кэша и размера состояния. Рядом на SQL-кластере работает задание с ForSt и асинхронным доступом к состоянию. Java-код в этом уроке не меняется, правки только в Compose, скриптах и SQL. Задание урока решается расчётом, файлов для него создавать не нужно.

Шаг 1. Настройки памяти и метрики RocksDB

В docker-compose.yml к общему блоку Flink добавляются девять строк.

ПРОСТЫМИ СЛОВАМИ

Доля managed memory записана явно, хотя 0,4 и так значение по умолчанию. Так она видна в конфиге, и её удобно менять для экспериментов.

RocksDB живёт в бюджете managed memory слота. Это тоже значение по умолчанию, строка нужна как напоминание, что выключать его в контейнере опасно.

Две метрики кэша, ёмкость и занятый объём. В занятый входят и memtable, потому что менеджер буферов записи учитывает их в том же кэше.

Оценка числа ключей и объёма живых данных в SST-файлах каждого состояния.

Число идущих компакций и счётчик фоновых ошибок. Вторая метрика выше нуля значит, что RocksDB не может писать, чаще всего кончился диск.

Замер задержек обращений к состоянию, например чтения и записи ValueState. Ключ записан старым именем, о нём ниже.

Все нативные метрики RocksDB выключены по умолчанию, и включать их стоит выборочно. Каждая метрика это опрос свойства RocksDB по каждому состоянию каждой подзадачи.

В исходниках

Ключ замера задержек в Flink 2.2 называется state.latency-track.keyed-state-enabled. Имя с state.backend осталось как устаревшее и пока принимается.

Работает и старый ключ, но в новых конфигах пиши новое имя. Устаревшие ключи однажды убирают, и тогда настройка молча перестанет действовать.

Шаг 4. Метрики RocksDB

Через минуту работы спроси у Prometheus метрики состояния profile, это профиль карты из CardProfileFunction. Имя состояния входит в имя метрики, поэтому регулярное выражение отбирает все метрики RocksDB этого состояния.

curl -s localhost:9090/api/v1/query \
  --data-urlencode 'query={__name__=~"flink_taskmanager_job_task_operator_profile_rocksdb_.*"}' \
  | jq -r '.data.result[] | "\(.metric.__name__) \(.value[1])"'

Флаг --data-urlencode кодирует фигурные скобки и кавычки запроса для URL. Prometheus вернёт по строке на каждую метрику каждой подзадачи. Через 60 секунд при 200 платежах в секунду значения были такими.

МетрикаЗначениеКак читать
rocksdb_estimate_num_keys8563Оценка RocksDB. Генератор выдаёт 5000 карт, поэтому для точного счёта ключей она не годится, только для порядка величины
rocksdb_estimate_live_data_size41162 байтаДанные в SST-файлах. Почти всё записанное за минуту ещё лежит в memtable, поэтому число маленькое

Сочетание последних двух строк объясняет, как читать кэш. Ёмкость фиксирована, а заполнение растёт, пока не упрётся в неё. Если usage долго стоит у capacity, а задержки чтения из замера состояния растут, кэша не хватает. На стенде с 5000 картами до этого далеко. Метрики num_running_compactions и background_errors полезны в алертах урока 17. Первая показывает, не захлёбывается ли RocksDB компакциями, вторая обязана быть нулём.

Шаг 5. Когда память не сходится

Проверим на себе, как выглядит конфликт. Временно поменяй в общем блоке FLINK_PROPERTIES значение taskmanager.memory.process.size на 1g и добавь строку taskmanager.memory.flink.size: 2g. JobManager эти ключи не читает, упадёт только TaskManager. Пересоздай контейнеры и открой лог.

docker compose up -d
docker compose logs taskmanager | grep -A1 IllegalConfigurationException
IllegalConfigurationException: TaskManager memory configuration failed: The configured Total Process Memory size (1024.000mb ...) is less than the sum of the derived Total Flink Memory size (2.000gb ...)

Это ветка из цитаты deriveJvmOverheadFromTotalFlinkMemoryAndOtherComponents. Явный Total Flink важнее размера процесса, и Overhead считается разностью, которая здесь отрицательна. Кнопка «process 1g и flink 2g» в калькуляторе выдаёт ту же ошибку. Из урока 1 ты знаешь второй случай. Старый конфиг с явными кучей задач, managed и Total Flink оставлял сети 0 байт, и TaskManager падал с Derived Network Memory size (0 bytes) is not in configured Network Memory range. Его воспроизводит третья кнопка. Лечение в обоих случаях одно, убрать лишние явные размеры и оставить process.size. Верни строки как были, выполни docker compose up -d --wait и отправь задание заново.

Шаг 6. ForSt на SQL-кластере

Асинхронный доступ к состоянию проще всего попробовать в SQL, где не нужно переписывать функции. Создай sql/merchant_revenue_forst.sql. Это тот же подсчёт выручки продавцов из урока 14, только без окна, чтобы агрегат держал состояние постоянно.

Две строки SET в начале работают только для этого задания. state.backend.type заменяет RocksDB из конфига SQL-кластера на ForSt, table.exec.async-state.enabled выбирает асинхронные версии операторов. Мини-пакеты и двухфазную агрегацию асинхронный режим пока не поддерживает, у нас они и так выключены. Таблица для результата добавляется в sql/init.sql.

Postgres выполняет init.sql только при первом запуске на пустой базе. Если контейнер живёт с прошлых уроков, новой таблицы в нём нет. Проще всего пересоздать стенд командой docker compose --profile sql down -v и поднять заново. Флаг -v удаляет анонимные тома контейнеров, каталог data с чекпоинтами остаётся. После этого повтори команды шага 3.

docker compose --profile sql up -d --wait
docker compose --profile sql exec -T sql-jobmanager sql-client.sh -f /sql/merchant_revenue_forst.sql

Флаг -T отключает псевдотерминал, он не нужен, когда SQL Client читает файл. Через пару минут проверь, какой бэкенд достался заданию и как идут его чекпоинты.

job=$(curl -s localhost:8082/jobs/overview \
  | jq -r '.jobs[] | select(.name == "payguard-sql-forst" and .state == "RUNNING") | .jid')
curl -s localhost:8082/jobs/$job/checkpoints/config | jq -r .state_backend
FLINK_REST=http://localhost:8082 scripts/checkpoint-report.sh
docker compose exec postgres psql -U payguard -d payguard \
  -c "select count(*), sum(payment_count) from merchant_revenue_forst"

Задание ищется по имени из pipeline.name, потому что на SQL-кластере могут работать задания прошлых уроков. Скрипт checkpoint-report.sh берёт первое запущенное задание, если там их несколько, смотри историю чекпоинтов в Web UI на 8082. На стенде state_backend вернул ForStStateBackend. Чекпоинты занимали 32-41 мс при размере 118-125 КиБ, в графе была вершина GroupAggregate[4], а в таблице оказалось 50 продавцов и 16200 платежей.

Маленький размер чекпоинта здесь не заслуга ForSt, у 50 продавцов просто мало состояния. Основной каталог ForSt по умолчанию совпадает с каталогом чекпоинтов, у нас это локальный том /flink-data/sql-checkpoints. В проде там был бы S3, и выгода от лёгкого восстановления появилась бы на гигабайтах состояния. Останови задание, когда насмотришься, через Web UI или flink cancel.
