Треть платежей у одного продавца

PayGuard должен держать по каждому продавцу накопительный итог. Для этого все платежи одного продавца обязаны приходить в одну и ту же параллельную копию оператора, иначе итог разъедется по нескольким местам. В Spark ту же задачу решает shuffle по ключу перед агрегацией.

В генераторе есть подвох, и он взят из жизни. У любого маркетплейса или платёжного агрегатора найдётся крупный продавец, через которого идёт заметная доля оборота. У нас это m-0000, на него приходится 30 % платежей.

Если все платежи m-0000 обязаны попасть в одну подзадачу, эта подзадача получит минимум треть нагрузки, сколько бы их ни было. В уроке разберём, как Flink выбирает подзадачу для ключа, как записи физически едут по сети и почему одна перегруженная подзадача замедляет соседей.

Гардероб в театре

Представь гардероб на 128 крючков и несколько гардеробщиков. Номер крючка для пальто выбирают по фамилии зрителя по жёсткому правилу, поэтому одно и то же пальто всегда висит на одном крючке. Каждый гардеробщик отвечает за непрерывный ряд крючков. Двое делят ряд пополам, четверо берут по 32 крючка.

Если в зал пришёл ещё один гардеробщик, пальто никто не перевешивает. Меняются только границы рядов, и часть крючков переходит к новому человеку целиком, вместе с пальто. Число крючков при этом поменять нельзя, они прибиты к стене.

Во Flink крючки называются группами ключей (key group), гардеробщики это подзадачи оператора после keyBy, а пальто это состояние ключа. Если пришёл автобус туристов с одной фамилией, всё ляжет на один крючок, и разгребать очередь будет один гардеробщик. Это перекос ключей.

keyBy и группы ключей

Метод keyBy объявляет, что дальше поток разбит по ключу. Сам он ничего не считает, он ставит на ребро графа стратегию распределения (partitioner) KeyGroupStreamPartitioner. Для каждой записи она делает два шага.

  1. Номер группы ключей. keyGroup = murmurHash(key.hashCode()) % maxParallelism. Здесь key.hashCode() это обычный Java-хеш ключа, а murmurHash перемешивает его биты, чтобы похожие строки не легли в соседние группы. maxParallelism задаёт число групп, по умолчанию 128.
  2. Номер подзадачи. subtask = keyGroup * parallelism / maxParallelism в целых числах. Группы нарезаются непрерывными диапазонами, при параллелизме 4 подзадача 0 получает группы 0-31, подзадача 1 группы 32-63 и так далее.

Посчитаем вручную для нашего горячего продавца. Числа проверены вызовом KeyGroupRangeAssignment из flink-runtime 2.2.1 и отдельным расчётом на Python.

Хеши у двух строк почти одинаковые, отличаются на 7. После murmurHash они расходятся далеко, это и есть смысл второго хеширования. Обрати внимание, что номер группы от параллелизма не зависит. При смене параллелизма меняется только то, какая подзадача владеет группой 18.

В исходниках

Обе формулы живут в классе KeyGroupRangeAssignment. Сначала ключ превращается в номер группы, на вход идёт обычный hashCode().

Потом группа превращается в номер подзадачи одной целочисленной формулой.

Сама стратегия на ребре берёт ключ из записи и вызывает эту функцию. Число каналов numberOfChannels равно параллелизму получателя.

Отсюда следует требование к ключу. Его hashCode() должен давать одно и то же число в разных JVM. У String, Long и record из строк так и есть. Хеш по умолчанию из Object зависит от конкретного объекта, и одинаковые ключи на разных машинах уйдут в разные подзадачи. Документация прямо запрещает ключи без переопределённого hashCode() и массивы.

Максимальный параллелизм выбирают один раз

Группа ключей это единица, которой Flink переносит состояние при смене параллелизма. Отсюда два последствия. Параллелизм оператора с состоянием не может превысить maxParallelism, потому что подзадаче без единой группы нечего делать. И сменить maxParallelism после первого запуска без потери состояния нельзя, ведь от него зависит номер группы каждого ключа.

В исходниках

Если maxParallelism не задан, планировщик вычисляет его из параллелизма вершины.

Формула берёт полтора параллелизма, округляет вверх до степени двойки и держит результат в пределах от 128 до 32768.

Мы вызвали эту функцию для разных значений. До параллелизма 85 включительно получается 128, при 86 уже 256, при 200 получается 512. На странице Production Readiness написано, что 128 выдаётся для любого параллелизма до 128. Код с этим расходится, верь коду.

⚠
Задай maxParallelism до первого запуска в прод

Задание стартовало с параллелизмом 100 и без явной настройки получило 256 групп. Через год нагрузка выросла, и нужен параллелизм 300. Без потери состояния это невозможно. Выбери число с запасом на рост, например 1024 или 4096, и задай его через env.setMaxParallelism или ключ pipeline.max-parallelism. Слишком большое число тоже вредно, часть структур бэкенда состояния растёт вместе с числом групп.

В Spark Structured Streaming похожее ограничение устроено жёстче. Состояние там разбито хешем ключа на spark.sql.shuffle.partitions частей, и документация запрещает менять эту настройку после первого запуска запроса. Во Flink неизменно число групп, а параллелизм можно менять в его пределах.

Другие способы раздать записи

Ключ нужен не всегда. Если оператор работает с каждой записью отдельно, записи можно раздавать так, как удобнее сети. У каждого способа есть имя, которое Web UI пишет на ребре между вершинами.

Если ты ничего не указал, Flink выбирает сам. При одинаковом параллелизме соседей ставится FORWARD, при разном REBALANCE. Если явно попросить forward() между операторами с разным параллелизмом, задание упадёт ещё при построении графа.

В исходниках

Правило выбора по умолчанию и проверка для FORWARD находятся в одном методе StreamGraph.

REBALANCE начинает со случайного канала, чтобы разные отправители не били в одного получателя одновременно, и дальше идёт по кругу.

RESCALE устроен так же внутри одного отправителя, а подмножество получателей определяется при построении графа исполнения. Если получателей больше, отправитель с номером partitionNum кормит непрерывный кусок из numConsumers подзадач.

Имя на ребре в Web UI это результат toString() стратегии, поэтому там видны именно HASH, REBALANCE и FORWARD.

Куда уходят платежи

Нажми кнопку, и платежи разойдутся по подзадачам.

При HASH и четырёх получателях одна подзадача получает больше других даже без горячего ключа. 50 ключей это мало, и на четыре подзадачи они легли как 8, 14, 11 и 17. Где рвётся цепочка

Из урока 2 ты помнишь, что соседние операторы склеиваются в цепочку и работают в одном потоке. Склейка возможна только на ребре FORWARD. Любой из способов выше, кроме forward, разрывает цепочку, потому что запись может уйти в другую подзадачу, а значит в другой поток или на другую машину. Ещё цепочку рвут разный параллелизм, разные группы слотов, вызовы startNewChain() и disableChaining().

В PayGuard после этого урока две вершины. Первая заканчивается на to-merchant-total, вторая начинается с merchant-running-total, между ними ребро HASH.

В исходниках

Внутри цепочки запись передаётся следующему оператору обычным вызовом метода. Сериализации, буферов и сети здесь нет, счётчики увеличиваются и сразу вызывается обработчик.

На разрыве цепочки запись проходит весь путь, о котором ниже. Её сериализуют в байты, копят в сетевом буфере, передают и разбирают на другой стороне. Поэтому лишний rebalance() между простыми операторами стоит заметно дороже самого оператора.
