Что будет в конце

Задание считает накопительный итог по каждому продавцу через keyBy и reduce. Ты увидишь в REST, что цепочка разорвалась на две вершины, и найдёшь в метриках перекос, который заранее предскажешь по формуле. Файлы задания KeyDistribution и его тест пока не создавай, они понадобятся на следующей вкладке.

Шаг 1. Модель итога

Создай src/main/java/dev/study/payguard/model/MerchantTotal.java. Это record с тремя полями и двумя методами. of превращает один платёж в итог из одной записи, plus складывает два итога одного продавца.

Итог неизменяемый, plus возвращает новый объект. Так безопаснее, потому что reduce хранит предыдущий итог в состоянии, и случайная правка старого объекта испортила бы его. Record из простых полей Flink сериализует своим сериализатором без Kryo, это ты проверял в уроке 3.

Шаг 2. keyBy и reduce в задании

В PayGuardJob печать сырых платежей заменяется на подсчёт итогов.

ПРОСТЫМИ СЛОВАМИ

Каждый платёж превращаем в итог из одной записи. Это обычный map, он склеится в цепочку с разбором, потому что параллелизм тот же и ребро FORWARD.

Имя и uid даём сразу. Имя будет видно в Web UI, а uid понадобится состоянию в уроке 13.

keyBy ставит на ребро стратегию HASH по merchantId. Здесь цепочка рвётся, дальше записи пойдут по сети.

reduce складывает новый итог с предыдущим итогом того же продавца. Предыдущий хранится в состоянии с ключом.

У reduce тоже имя и uid. Это оператор с состоянием, для него uid обязателен.

Каждый обновлённый итог печатаем. print склеится с reduce во вторую вершину.

В исходниках

Посмотрим, что делает оператор за reduce. Предыдущее значение лежит в ValueState, это состояние с ключом, и оно своё у каждого продавца. Результат уходит дальше на каждой записи, поэтому в выводе будет поток постепенно растущих итогов.

Состояние разбито по группам ключей так же, как поток. Поэтому подзадача, которая получает платежи m-0000, держит и его итог, и сетевых обращений к чужому состоянию нет.

Шаг 5. Метрики по подзадачам

Пройди по обеим вершинам и запроси метрики, сведённые по подзадачам. Параметр agg=min,max,sum возвращает минимум, максимум и сумму, а разница между минимумом и максимумом и есть перекос.

for V in $(curl -s localhost:8081/jobs/$JOB | jq -r '.vertices[].id'); do
  curl -s "localhost:8081/jobs/$JOB/vertices/$V/subtasks/metrics?get=numRecordsIn,numRecordsOut,busyTimeMsPerSecond,backPressuredTimeMsPerSecond&agg=min,max,sum" | jq -c .
done
[{"id":"numRecordsIn","min":7600.0,"max":10180.0,"sum":17780.0},{"id":"numRecordsOut","min":7600.0,"max":10180.0,"sum":17780.0},{"id":"busyTimeMsPerSecond","min":2.0,"max":3.0,"sum":5.0},{"id":"backPressuredTimeMsPerSecond","min":0.0,"max":0.0,"sum":0.0}]
[{"id":"numRecordsIn","min":7037.0,"max":10560.0,"sum":17597.0},{"id":"numRecordsOut","min":0.0,"max":0.0,"sum":0.0},{"id":"busyTimeMsPerSecond","min":5.0,"max":6.0,"sum":11.0},{"id":"backPressuredTimeMsPerSecond","min":0.0,"max":0.0,"sum":0.0}]

Первая строка относится к вершине с источником. Неравномерность 7600 против 10180 здесь появилась ещё в Kafka. Каждая подзадача источника читает две партиции из четырёх, и партиции заполнены неодинаково. До keyBy ключ на раскладку не влияет. Выход вершины теперь ненулевой, потому что записи уходят в сеть ко второй вершине. Это видно по счётчику numRecordsOut.

Вторая строка относится к вершине с reduce. Сюда попало 17597 записей, на 183 меньше, чем вышло из первой. Это около 1 %, примерно столько битых записей ушло в DLQ, плюс счётчики двух вершин сняты не в один момент. Выход нулевой, потому что последний оператор цепочки печатает в stdout и дальше ничего не отправляет. busy в обеих вершинах единицы миллисекунд, а backpressure ноль, так что при такой нагрузке перекос безвреден. При нагрузке, которую подзадача не тянет, он превратится в backpressure по механизму из теории.

Шаг 6. Предскажи перекос заранее

Перекос во второй вершине можно посчитать, не запуская кластер. По формуле из теории при параллелизме 2 и 128 группах из 50 продавцов в подзадачу 0 попадают 22, включая m-0000 с его группой 18, а в подзадачу 1 попадают 28.

Теперь доли. На m-0000 приходится 30 % потока, на каждого из 49 остальных 70 / 49 = 1,43 %. Подзадача 0 получает 30 % + 21 × 1,43 % = 60 %, подзадача 1 получает 28 × 1,43 % = 40 %. От 17597 записей это 10558 и 7039. В метриках стоят 10560 и 7037. Формула и генератор сошлись почти до записи.

Обрати внимание на неожиданность. Без горячего ключа перекос был бы обратным, у подзадачи 1 больше продавцов. Горячий продавец перевесил.

Шаг 7. Посмотри своими глазами

Открой http://localhost:8081, зайди в задание и посмотри на граф. Между двумя вершинами на ребре написано HASH. Нажми на вторую вершину, вкладка Metrics или Subtasks покажет те же числа numRecordsIn по каждой подзадаче.

Предсказание можно проверить и по логу. Префикс перед строкой print это номер подзадачи плюс один, а m-0000 по расчёту живёт в подзадаче 0.

docker compose logs taskmanager | grep -oE '[0-9]+> MerchantTotal\[merchantId=m-0000' | sort | uniq -c

Ты должен увидеть одну строку с префиксом 1> и большим счётчиком. Строк с 2> для этого продавца быть не может. Итоги выглядят как MerchantTotal[merchantId=..., paymentCount=..., amountMinor=...], это стандартный toString record, и paymentCount у одного продавца только растёт.
