Что будет в конце

Источник Kafka сам разбирает JSON и ставит каждому платежу метку времени из eventTimeMs. Watermark считается по каждой партиции с допуском 10 секунд, а молчащая минуту партиция перестаёт его держать. Ты найдёшь watermark в REST и в Web UI и поймёшь, почему у источника его не видно. Пробу опозданий напишешь в задании, её файлы сейчас создавать не нужно.

Новых зависимостей нет, build.gradle.kts не меняется.

Шаг 1. Результат разбора

Схема десериализации обязана вернуть один объект на запись. Битая запись тоже должна дойти до DLQ, поэтому заводим обёртку, в которой заполнено ровно одно поле. Создай model/ParsedRecord.java.

Это public record из двух полей-record, поэтому Flink сериализует его без Kryo, и запрет generic-типов из урока 3 продолжает действовать.

Шаг 2. Разбор в источнике

Создай pipeline/ParsedRecordSchema.java. Класс PaymentValidator из урока 3 остаётся как был.

ПРОСТЫМИ СЛОВАМИ

AbstractDeserializationSchema берёт на себя описание типа результата. Её конструктор выводит тип ParsedRecord из параметра класса через TypeExtractor, наследнику остаётся написать deserialize.

Схема, как и функция, сериализуется на клиенте и едет в TaskManager. ObjectMapper создаётся в open, уже внутри подзадачи.

Байты превращаются в строку, затем в PaymentEvent. Валидатор из урока 3 решает, годится ли платёж. Годный оборачивается в accepted, негодный в rejected с причиной.

Синтаксическая ошибка JSON перехватывается и становится записью с причиной bad-json. Исключение из deserialize уронило бы задачу, эмиттер Kafka заворачивает его в IOException.

Время отказа берётся с часов машины, это момент разбора, его видно в DLQ.

Старый ParsePaymentFunction и его тест удали, их работу теперь делают схема и следующий класс. Новый тест схемы проверяет те же три случая.

Схеме не нужен тестовый стенд, это обычный объект. В open передаётся null, потому что наш метод контекст не читает.

Шаг 3. Развилка после источника

Из источника выходит ParsedRecord. Разведём его на поток платежей и побочный выход отказов. Создай pipeline/SplitParsedRecords.java.

Метка REJECTED и способ работы с побочным выходом те же, что в уроке 3. Функция стала проще, потому что разбирать ей больше нечего.

Шаг 4. Стратегия watermark

Создай pipeline/PaymentWatermarks.java. Это единственное место, где задание решает, что такое время.

ПРОСТЫМИ СЛОВАМИ

Допуск беспорядка 10 секунд и таймаут простоя одна минута вынесены в публичные константы, чтобы их было видно с первого взгляда и можно было взять в тестах.

forBoundedOutOfOrderness создаёт генератор, который мы разобрали в теории. Явный параметр <ParsedRecord> нужен компилятору, иначе он не узнает тип записи в лямбде ниже.

TimestampAssigner получает запись и метку Kafka. Принятому платежу ставится его eventTimeMs. У отказа времени события нет, и он берёт метку Kafka. Генератор не задаёт её сам, поэтому её ставит продюсер в момент отправки, и она близка к текущему времени.

withIdleness оборачивает генератор проверкой простоя. Партиция без записей дольше минуты перестаёт держать общий watermark.

Отказы тоже двигают watermark, ведь генератор видит все записи сплита. Их метка Kafka почти совпадает с текущим временем, поэтому watermark от них не убегает вперёд.

Шаг 5. Задание

Открой PayGuardJob. Источник теперь отдаёт ParsedRecord, а вместо noWatermarks передаётся наша стратегия. Начало метода main выглядит так.

Метод сборки источника меняет тип и схему.

Подсчёт сумм по продавцам из урока 4 остаётся прежним. До задания подключи его прямо к переменной split, то есть цепочка начинается с split.map(MerchantTotal::of). В задании между ними встанет проба.

Оператор переименован в split-parsed и получил новый uid. Состояния у прежнего оператора не было, и чекпоинтов в проекте пока нет, поэтому смена uid ничего не ломает. В уроке 13 мы увидим, когда это опасно.

Шаг 7. Watermark в REST

У каждой вершины графа есть ресурс /watermarks. Пройдём по всем вершинам задания. Первая строка находит идентификатор работающего задания, цикл берёт идентификаторы вершин, а jq -c '[.[].value]' оставляет из ответа только значения по подзадачам.

JOB=$(curl -s localhost:8081/jobs | jq -r '.jobs[] | select(.status == "RUNNING") | .id')
for V in $(curl -s localhost:8081/jobs/$JOB | jq -r '.vertices[].id'); do
  curl -s localhost:8081/jobs/$JOB/vertices/$V/watermarks | jq -c '[.[].value]'
done
[]
["1794085494920","1794085494920"]

Первая строка относится к вершине с источником, вторая к вершине merchant-running-total. Значение это миллисекунды от начала эпохи Unix, 7 ноября 2026 года, 21:04:54.920 по UTC. Команда date -r 1794085494 на macOS переведёт его в твой часовой пояс. Обе подзадачи показывают одно число, как и на схеме из теории.

Пустой список у источника выглядит как поломка, хотя watermark там есть. Причина в том, что именно отдаёт этот ресурс.

В исходниках

Обработчик REST читает у каждой подзадачи одну метрику уровня задачи, currentInputWatermark.

Эту метрику на уровне задачи регистрирует задача с сетевым входом. Код ниже из OneInputStreamTask. В задаче источника такой регистрации нет, у неё нет входа из сети.

Поэтому watermark источника видно только по вершине, которая его получила. У операторов внутри цепочки есть своя метрика с тем же именем на уровне оператора. Её регистрирует OperatorChain, в списке метрик подзадачи она начинается с имени оператора, например split-parsed.

Шаг 8. Watermark в Web UI

Открой http://localhost:8081 и задание payguard. На прямоугольнике вершины merchant-running-total есть строка Low Watermark. Щёлкни по вершине, в нижней панели открой вкладку Watermarks. Там значения по подзадачам и рядом дата в часовом поясе браузера.

В исходниках

Web UI берёт тот же ресурс REST и считает Low Watermark как минимум по подзадачам. Значение не больше Long.MIN_VALUE превращается в «нет watermark».

Отсюда два практических вывода. У вершины источника строки Low Watermark не будет, список пуст. Если вместо числа во вкладке написано No Watermark (Watermarks are only available if EventTime is used), вершина получила только начальное значение Long.MIN_VALUE. Так было в уроках 1-4 с noWatermarks, и так бывает, когда ни одна партиция ещё ничего не прислала.

Как читать число. Сравни watermark с текущим временем. Разница около 10 секунд значит, что всё в порядке, это наш допуск. Разница, которая растёт, значит, что одна партиция отстала или замолчала, а таймаут простоя ещё не истёк.
