Что будет в конце

Рядом с основным кластером работает второй, для SQL. На нём запущено задание из файла sql/merchant_revenue.sql, которое пишет выручку продавцов по минутам в таблицу PostgreSQL. Java-кода в этой части нет, и build.gradle.kts пока не меняется. Файлы src/main/resources/sql/risk_revenue.sql и SqlJobRunner.java относятся к заданию, сейчас их создавать не нужно.

Шаг 1. Почему нельзя добавить коннектор в общий образ

Простой путь это положить flink-sql-connector-kafka в lib/ основного кластера. Тогда отправка нашего DataStream-задания перестаёт проходить.

java.lang.NoSuchMethodError: ...OffsetsInitializer.committedOffsets(org.apache.kafka.clients.consumer.OffsetResetStrategy)

Причину мы разобрали в теории. Класс org.apache.flink.* пришёл из lib/, его метод ждёт перепакованный тип, а задание скомпилировано с обычным. Лечение здесь архитектурное. SQL живёт на отдельном кластере со своим образом, DataStream-задания остаются на старом.

Шаг 2. Образ с коннекторами

Создай docker/Dockerfile.

Инструкция ADD скачивает файл по URL прямо при сборке образа, а --chown отдаёт его пользователю flink, от имени которого работает процесс. В lib/ ложатся толстый коннектор Kafka, две части JDBC-коннектора и драйвер PostgreSQL.

Две последние строки появились после реальной ошибки. Без них SQL с JDBC-коннектором завершается так.

[ERROR] Could not execute SQL statement. Reason: java.lang.ClassNotFoundException: io.openlineage.client.utils.jdbc.JdbcExtractor

OpenLineage это библиотека для отслеживания происхождения данных. В POM артефакта flink-connector-jdbc-core версии 4.1.0-2.2 она указана обычной зависимостью, поэтому в его jar не входит. В образ её надо добавить отдельно, это файлы openlineage-java и openlineage-sql-java 1.32.0.

Шаг 3. Второй кластер в Compose

Добавь в docker-compose.yml общий блок настроек и две службы.

ПРОСТЫМИ СЛОВАМИ

x-flink-sql-common это YAML-якорь, общий кусок настроек для двух служб. Compose игнорирует ключи с префиксом x- и разрешает на них ссылаться.

image вместе с build велит собрать образ из папки docker и дать ему имя.

profiles: [sql] означает, что службы стартуют только при флаге --profile sql. Обычный docker compose up их не трогает.

jobmanager.rpc.address указывает на собственный JobManager этого кластера. Память и слоты задаём отдельно от основного.

Бэкенд RocksDB и чекпоинты каждые 15 с работают для SQL так же, как для DataStream. Каталог свой, чтобы снимки двух кластеров не смешивались.

Папка ./sql смонтирована только для чтения, из неё клиент возьмёт скрипт.

Порт JobManager отображён на 8082, основной кластер остаётся на 8081.

Шаг 4. Таблица в PostgreSQL

Допиши таблицу результата в конец sql/init.sql.

Первичный ключ здесь совпадает с ключом в DDL Flink, по нему идёт upsert. Образ PostgreSQL выполняет init.sql только при пустом каталоге данных. Если стенд уже поднимался, сначала останови его командой docker compose --profile sql down, тогда новый контейнер создаст таблицы заново.

Шаг 5. Запрос

Создай sql/merchant_revenue.sql.

Разберём объявление источника.

ПРОСТЫМИ СЛОВАМИ

Поля повторяют JSON нашего PaymentEvent, поэтому имена в camelCase.

event_time это вычисляемая колонка. TO_TIMESTAMP_LTZ превращает миллисекунды в метку времени, и в сообщении Kafka такого поля нет.

WATERMARK FOR делает колонку атрибутом времени события и разрешает опоздание на 10 с. Этот же приём из урока 5 здесь занимает одну строку.

connector, topic и адрес брокера связывают таблицу с топиком. Сама таблица данных не хранит.

latest-offset велит читать только новые записи при первом запуске.

json.ignore-parse-errors пропускает записи и поля с ошибками разбора вместо падения задания. Нашей DLQ из урока 3 в этом запросе нет, поэтому битые записи никуда не сохраняются.

Приёмник merchant_revenue_1m объявлен с PRIMARY KEY ... NOT ENFORCED. Эти слова значат, что Flink не проверяет уникальность сам и верит, что её обеспечивает внешняя система. SET 'pipeline.name' задаёт имя задания, которое ты увидишь в Web UI.

Шаг 6. Запусти

Порядок команд прежний, сначала сборка, потом Compose. Иначе смонтируется пустая build/libs.

./gradlew shadowJar
docker compose --profile sql up -d --wait
docker compose --profile sql exec sql-jobmanager sql-client.sh -f /sql/merchant_revenue.sql

Флаг --profile sql включает службы профиля вместе с обычными, поэтому поднимутся оба кластера. Первый запуск дольше из-за сборки образа. Флаг -f у SQL Client выполняет файл по одной инструкции и завершается на первой ошибке. INSERT клиент по умолчанию выполняет асинхронно, то есть отправляет задание и выходит, а оно продолжает работать на кластере. Открой http://localhost:8082 и убедись, что задание payguard-sql-revenue работает.

Дай нагрузку.

./gradlew loadgen --args="--rate 200"

Генератор занимает терминал, поэтому через пару минут посмотри на результат из второго.

docker compose exec postgres psql -U payguard -d payguard \
  -c "SELECT count(*) AS rows_total, sum(payment_count) AS payments FROM merchant_revenue_1m"
docker compose exec postgres psql -U payguard -d payguard \
  -c "SELECT * FROM merchant_revenue_1m ORDER BY amount_minor DESC LIMIT 5"

В нашем прогоне за 100 с при 200 платежах в секунду таблица получила 100 строк с суммой 15423 платежа. Цифры объясняются так. Продавцов 50, значит, закрылось две минуты. 15423 платежа при такой скорости это около 77 с потока. Остальные ещё лежали в открытом окне или были отброшены как опоздавшие, потому что генератор задерживает часть платежей на срок до 30 с, а водяной знак разрешает 10 с. Пока первая минута не закроется, строк в таблице не будет совсем. Во втором запросе первым должен стоять m-0000, ему генератор отдаёт 30 % платежей.

Шаг 7. Посмотри на changelog своими глазами

Необязательный эксперимент. Запусти клиент без -f командой docker compose --profile sql exec sql-jobmanager sql-client.sh, вставь CREATE TABLE payments из скрипта и выполни два запроса ниже.

SET 'sql-client.execution.result-mode' = 'tableau';
SELECT merchantId, COUNT(*) AS cnt FROM payments GROUP BY merchantId;

EXPLAIN CHANGELOG_MODE
SELECT merchantId, window_start, COUNT(*)
FROM TABLE(TUMBLE(TABLE payments, DESCRIPTOR(event_time), INTERVAL '1' MINUTE))
GROUP BY merchantId, window_start, window_end;

Режим tableau печатает результат прямо в терминал с колонкой op, в ней появятся пометки +I, -U и +U. Запрос останови через Ctrl+C. Вывод EXPLAIN CHANGELOG_MODE показывает для каждого узла поле changelogMode. Мы выполнили EXPLAIN CHANGELOG_MODE для обоих запросов на стенде. Ниже раздел Optimized Physical Plan, длинные списки полей у источника обрезаны.

GroupAggregate(groupBy=[merchantId], select=[merchantId, COUNT(*) AS cnt], changelogMode=[I,UA])
+- Exchange(distribution=[hash[merchantId]], changelogMode=[I])
   +- Calc(select=[merchantId], changelogMode=[I])
      +- TableSourceScan(table=[[default_catalog, default_database, payments, ...]], ..., changelogMode=[I])
Calc(select=[merchantId, window_start, EXPR$2], changelogMode=[I])
+- GlobalWindowAggregate(groupBy=[merchantId], window=[TUMBLE(slice_end=[$slice_end], size=[1 min])], ..., changelogMode=[I])
   +- Exchange(distribution=[hash[merchantId]], changelogMode=[I])
      +- LocalWindowAggregate(groupBy=[merchantId], window=[TUMBLE(time_col=[event_time], size=[1 min])], ..., changelogMode=[I])
         +- Calc(select=[merchantId, Reinterpret(TO_TIMESTAMP_LTZ(eventTimeMs, 3)) AS event_time], changelogMode=[I])
            +- TableSourceScan(table=[[default_catalog, default_database, payments, ...]], ..., changelogMode=[I])

Читай снизу вверх. Источник Kafka в обоих планах выдаёт только вставки, I. Обычная агрегация на выходе даёт [I,UA], то есть вставку и обновление после изменения (+U). Каждый новый платёж меняет уже выданный счётчик продавца, поэтому такой поток примет только приёмник с поддержкой upsert. Оконная агрегация выдаёт только I. Окно закрывается по водяному знаку один раз, и его строка больше не меняется, поэтому результат можно писать даже в приёмник, который умеет только дописывать. Заодно видно, что оптимизатор сам разбил оконный запрос на две фазы. LocalWindowAggregate считает частичные суммы до обмена по сети, GlobalWindowAggregate складывает их после Exchange. Ту же схему для перекоса урок 18 строит руками на DataStream.
