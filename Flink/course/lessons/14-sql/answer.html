ПРОСТЫМИ СЛОВАМИ

Временное представление enriched дописывает к платежу уровень риска. FOR SYSTEM_TIME AS OF p.proc_time означает lookup join, запрос к справочнику на момент обработки записи.

LEFT JOIN и COALESCE сохраняют платёж неизвестного продавца с уровнем UNKNOWN. С обычным JOIN он бы пропал из выручки.

Внутренний запрос считает выручку по паре уровень и продавец в минутном окне, как в практике.

ROW_NUMBER нумерует продавцов внутри уровня и окна. В PARTITION BY стоят оба конца окна, поэтому планировщик выбирает оконный Top-N, который выдаёт итог один раз и чистит состояние.

WHERE top_rank <= 3 оставляет три верхних места.

Кэш настроен тремя опциями lookup.* в DDL таблицы merchants. Он снижает нагрузку на PostgreSQL, но новый уровень риска применится только после истечения записи, в нашем случае через 5 минут. Результат lookup join при этом не пересчитывается задним числом, так описывает этот join документация.

Запускающий класс.

Текст режется по точке с запятой в конце строки. Это простое решение со своим ограничением, точка с запятой в конце строки внутри литерала разрежет инструкцию. Для наших скриптов этого хватает. Метод withoutComments нужен, чтобы хвост из одних комментариев или пробелов не попал в executeSql. TableEnvironment.create со стриминговыми настройками работает без StreamExecutionEnvironment, потому что DataStream тут не нужен.

  -c dev.study.payguard.job.SqlJobRunner /jobs/payguard-1.0.0.jar --script risk_revenue.sql

Флаг -c задаёт главный класс вместо Main-Class из манифеста, а всё после пути к jar уходит аргументами в main. Команда down нужна только затем, чтобы PostgreSQL заново выполнил init.sql с новой таблицей. Она останавливает и задание из практики, запусти его снова, если оно нужно. Нагрузку даёт тот же ./gradlew loadgen --args="--rate 200" в отдельном терминале.

План нашего прогона выглядит так, те же имена ты увидишь в Web UI. Каждая строка это одна цепочка операторов, то есть одна вершина графа.

Source: payments[1] -> Calc[2] -> LookupJoin[3] -> Calc[4] -> LocalWindowAggregate[5]
GlobalWindowAggregate[7] -> Calc[8]
WindowRank[10] -> Calc[11] -> ConstraintEnforcer[12] -> Sink: risk_revenue[12]

Первая цепочка работает без обмена по сети, поэтому и lookup join, и локальная сумма выполняются в той же подзадаче, что читает Kafka. Calc это проекция и фильтр. Потом идёт обмен по ключу группировки, и GlobalWindowAggregate собирает частичные суммы. Следующий обмен ведёт в WindowRank, который строит топ.

В исходниках

Оператор ConstraintEnforcer в запросе никто не писал. Его добавляет сборка приёмника.

Это проверка ограничений приёмника, например NOT NULL. Какое действие выполнять при нарушении, определяет настройка, чьё значение передаётся здесь же.
