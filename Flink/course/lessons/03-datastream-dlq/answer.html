Ответ

Валидатор не знает о Flink и не бросает исключений. Отказ здесь это обычный результат, поэтому он возвращается как значение. Класс закрыт от других пакетов, потому что пользуется им только ParsePaymentFunction. Сериализатор ему не нужен, по потоку объекты этого класса не ходят.

Условия написаны как <= 0 из-за поведения Jackson. Отсутствующее поле типа long он заполняет нулём, а String значением null. Мы проверили это прогоном. Платёж без amountMinor уходит в DLQ с причиной non-positive-amount. Отличить отсутствие суммы от нулевой суммы при таких типах нельзя, для этого поле должно быть Long.

Тест обходится без тестового стенда и выполняется за миллисекунды. Функцию проверяем отдельно, там интересна только маршрутизация. Итог прогона всего снапшота на стенде курса выглядит так. В нём 11 тестов, это 4 из генератора, 2 из функции и 5 из валидатора.

Что снапшот пока не закрывает

Эти случаи в код курса не вошли, поэтому реши сам, закрывать ли их у себя. Все проверены прогоном на тестовом стенде и отдельными вызовами.

  • Текст null. Jackson возвращает Java null, и валидатор падает с NullPointerException, которое никто не ловит. В отличие от остальных битых записей, эта уронит задание. Добавь в функцию проверку payment == null перед вызовом валидатора и отправляй такую запись в DLQ с bad-json.
  • Лишние поля. Если новые поля партнёра не считаются ошибкой, настрой mapper через configure(DeserializationFeature.FAIL_ON_UNKNOWN_PROPERTIES, false) в open.
  • Tombstone в payments.raw. SimpleStringSchema падает раньше функции. Нужна своя схема, которая возвращает null для null, контракт такую запись пропускает.

Заодно можно закрепить типы тестом. Вызов PojoTestUtils.assertSerializedAsPojoWithoutKryo(PaymentEvent.class) из flink-test-utils проходит для наших record и падает, если в них появится поле UUID. Ошибка всплывёт при обычной сборке.
