Что будет в конце

Задание разбирает JSON в PaymentEvent, а непригодные записи отправляет в топик payments.dlq с причиной и временем. Настройки подключения приходят из аргументов командной строки. Функцию проверяют быстрые тесты без кластера. Бизнес-проверки платежа ты допишешь в задании, сегодня они будут пустой заглушкой.

Шаг 1. Зависимости

Открой build.gradle.kts. Появляются две группы зависимостей.

flink-json содержит JsonSerializationSchema, которой мы пишем в DLQ. Он идёт через flinkProvided, потому что файл flink-json лежит в папке lib/ дистрибутива Flink и в твой jar не нужен. Это видно по файлу сборки дистрибутива flink-dist/src/main/assemblies/bin.xml.

Строки с :tests подключают специальные артефакты с классами из тестового кода Flink. Классификатор tests означает отдельный jar рядом с основным. В них лежат OneInputStreamOperatorTestHarness и ProcessFunctionTestHarnesses, а flink-test-utils добавляет остальные утилиты, например PojoTestUtils.

Шаг 2. Запись для DLQ

Создай model/RejectedRecord.java. Это public record, поэтому Flink получит для него PojoTypeInfo, и запрет на generic-типы его не затронет.

Шаг 3. Функция разбора

Создай pipeline/ParsePaymentFunction.java.

ПРОСТЫМИ СЛОВАМИ

Метка побочного выхода. Пустые фигурные скобки создают анонимный подкласс, только так Flink узнаёт тип RejectedRecord. Поле публичное и статическое, потому что по нему же задание забирает поток.

Сама функция сериализуется на клиенте и едет в TaskManager. Поле transient в этом не участвует. Метод open создаёт ObjectMapper уже в подзадаче, свой на каждую.

processElement вызывается на каждую запись. Jackson собирает record из JSON через канонический конструктор, затем валидатор решает, принимать ли платёж.

Нормальный платёж идёт в основной выход через out.collect, с причиной отказа уходит в побочный.

Ошибка разбора перехватывается и становится обычной записью с кодом bad-json. Запись продолжает жизнь как данные и больше не роняет задачу.

Вспомогательный метод собирает RejectedRecord и пишет его через context.output с меткой. Время здесь берётся с часов машины, это момент отказа.

В строке с PaymentValidator.rejectionReason используется класс, который ты напишешь в задании, поэтому его файл с решением сейчас создавать не нужно. Чтобы код компилировался, положи рядом заглушку. Это класс PaymentValidator в том же пакете с одним статическим методом rejectionReason(PaymentEvent), который возвращает Optional.empty(). С ней любой разобранный платёж считается годным.

Шаг 4. Конфигурация и приёмник

До сих пор адреса были зашиты в код. JobConfig читает их из аргументов, значит, один и тот же jar подойдёт для любого стенда.

ParameterTool разбирает пары вида --dlq-topic имя. Значения по умолчанию подходят для нашего Compose, поэтому запуск без аргументов продолжит работать. Всё, что написано после имени jar в flink run, попадает в args.

Сборку приёмника вынесем в отдельный класс, она ещё пригодится для алертов.

JsonSerializationSchema превращает объект в JSON, топик задан заранее, а setDeliveryGuarantee включает режим повторной отправки, разобранный в теории. Ключ записи мы не задаём, распределением по партициям занимается продюсер Kafka.

Шаг 5. Задание

Перепиши PayGuardJob. Фильтр drop-blank из урока 2 больше не нужен, потому что пустая строка теперь получит причину bad-json. Также мы убрали печать плана, ты уже видел его в уроке 2.

ПРОСТЫМИ СЛОВАМИ

Читаем аргументы командной строки.

Запрещаем Kryo для всего задания. Настройка передаётся при создании окружения. Позже здесь появятся и другие параметры.

Источник тот же, а вместо фильтра стоит process. Результат нужно сохранить в переменную типа SingleOutputStreamOperator, потому что метод getSideOutput есть именно у него.

Из той же переменной забираем поток по метке и направляем его в Kafka. Явный параметр <RejectedRecord> нужен компилятору, чтобы вывести тип обобщённого метода.

Основной поток пока печатаем в лог, правила появятся позже. У всех операторов есть uid, зачем это нужно, обсуждали в уроке 2.

execute собирает граф, здесь и сработает проверка типов, и отправляет задание на кластер.

Шаг 6. Тест без кластера

Harness (тестовый стенд) это обёртка из тестового jar Flink, которая запускает один оператор прямо в JVM теста. Он отдаёт в функцию записи и показывает все её выходы, в том числе побочные.

ПРОСТЫМИ СЛОВАМИ

forProcessFunction создаёт и открывает стенд, поэтому open вызывать вручную не надо. Новый стенд перед каждым тестом исключает влияние тестов друг на друга.

Подаём корректный JSON. Второй аргумент processElement это время записи, здесь оно ни на что не влияет.

Сравниваем основной выход с ожидаемым объектом, record сам сравнивается по полям. Если в побочный выход ничего не писали, стенд возвращает для него null.

Подаём сломанный JSON. Основной выход пуст, а из очереди побочного выхода достаём запись и проверяем исходный текст и причину.

./gradlew test

Собери jar и подними стенд, порядок прежний. Если стенд уже работает, docker compose up ничего не сломает. Новый jar появится в смонтированной папке сам.

Если от прошлого урока осталось задание, останови его через flink cancel <JobID>. Теперь отправь новое и запусти генератор с одним процентом битых записей. Флаг --bad задаёт эту долю. Источник читает с конца топика, поэтому задание запускай первым.

Посмотрим на задание глазами REST. Сохрани его идентификатор в переменную и запроси описание.

JOB=$(curl -s localhost:8081/jobs | jq -r '.jobs[] | select(.status == "RUNNING") | .id')
curl -s localhost:8081/jobs/$JOB | jq -c '{name, state, vertices: [.vertices[] | {name, parallelism, status}]}'
{"name":"payguard","state":"RUNNING","vertices":[{"name":"Source: payments-raw -> parse-payment -> (dlq-sink: Writer -> dlq-sink: Committer, Sink: stdout)","parallelism":2,"status":"RUNNING"}]}

Вершина всего одна. Стрелки показывают цепочку операторов, а скобки обозначают развилку на два направления, это и есть основной и побочный выходы. Приёмник dlq-sink раскрылся в два оператора. Writer отправляет записи, а Committer нужен режиму exactly-once, в режиме AT_LEAST_ONCE его метод prepareCommit в KafkaWriter возвращает пустой список. Подробнее об этом поговорим в уроке 12.

Теперь метрики вершины по подзадачам. Параметр get перечисляет нужные счётчики, а agg просит сложить их по подзадачам.

curl -s "localhost:8081/jobs/$JOB/vertices/$V/subtasks/metrics?get=numRecordsIn,numRecordsOut,busyTimeMsPerSecond,backPressuredTimeMsPerSecond&agg=min,max,sum" | jq -c .
[{"id":"numRecordsIn","min":8573.0,"max":9207.0,"sum":17780.0},{"id":"numRecordsOut","min":84.0,"max":92.0,"sum":176.0},{"id":"busyTimeMsPerSecond","min":5.0,"max":6.0,"sum":11.0},{"id":"backPressuredTimeMsPerSecond","min":0.0,"max":0.0,"sum":0.0}]

Это числа с нашего стенда, у тебя они будут другими. На вход пришло 17780 записей, и они примерно поровну разошлись по двум подзадачам. Подзадачи заняты 5-6 мс в секунду, а обратного давления нет, запас огромный.

На выход вершины записано 176 записей, это около 1 %. На первый взгляд странно, ведь в stdout ушли почти все платежи. Причина в определении этого счётчика.

В исходниках

Оператор приёмника передаёт задаче свой счётчик. Комментарий объясняет смысл, это записи, отправленные во внешнюю систему.

Счётчик увеличивает код самого приёмника. Приёмник Kafka делает это на каждой отправке. В коде PrintSinkOutputWriter ни одного счётчика нет, поэтому stdout в сумму не попадает, и 176 здесь означает записи в DLQ.
