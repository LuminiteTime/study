RUNNING ещё ничего не гарантирует

Вернёмся к ночной аварии. Статус задания и состояние подзадач разные вещи, и разница видна в одном методе.

В исходниках

Планировщик сначала переводит задание в RUNNING и только потом запускает стратегию, которая просит слоты.

Подзадача считается работающей только после отчёта из потока на TaskManager. Сначала JobMaster отправляет описание подзадачи, TaskManager запускает поток, и уже поток проходит свои состояния.

Смотри на статус вершин в /jobs/<id>, в этом ответе видно настоящее положение дел. Этому полю мы и посвятим скрипт в задании.

Документация: REST API

Когда слотов не хватило

Кластер standalone не умеет сам поднимать новые TaskManager, ResourceManager распределяет только то, что уже подключилось. На Kubernetes или YARN он может запросить новые процессы. Поэтому в нашем стенде нехватка слотов кончается ошибкой, и поведение зависит от возраста кластера.

В исходниках

Первые минуты после старта кластер терпит нехватку, потому что TaskManager могут ещё подключаться. Длительность задаёт resourcemanager.standalone.start-up-time, а без него берётся slot.request.timeout, то есть пять минут.

После этого периода менеджер слотов сообщает о нехватке заданию сразу.

В пуле слотов этого задания такое уведомление отменяет все потоковые запросы, ожидающие слот.

Есть и вторая проверка, в самом JobMaster. Если запрос не удаётся выполнить в течение таймаута, он отменяется с другим текстом. Поэтому при поиске в логах проверяй обе строки.

Дальше решает стратегия перезапуска. Без чекпоинтов её значение по умолчанию это отсутствие перезапуска, с чекпоинтами это экспоненциальная задержка. В нашем задании чекпоинтов пока нет, поэтому оно перейдёт в FAILED. Этот сценарий мы в стенде не прогоняли, описание составлено по коду.

Документация: Configuration, Standalone

⚠
Частичный запуск тоже бывает

Планирование идёт по регионам, связанным передачей данных. У нашей цепочки нет связей между подзадачами, поэтому часть подзадач может получить слоты и успеть стартовать, пока остальные ждут. В этот момент задание читает только часть партиций Kafka, а смотреть в мониторинге надо на статус вершин.

Режимы Session и Application

Сегодня Flink разворачивается двумя способами. Они различаются временем жизни кластера и тем, где выполняется main. Третий режим per-job удалён во Flink 2.0, и в старых статьях он всё ещё встречается.

SessionApplication
КластерУже запущен и живёт независимо от заданийСоздаётся на приложение и останавливается вместе с ним
Где выполняется mainВ клиентеВ JobManager
ИзоляцияЗадания делят TaskManager, упавший процесс задевает всехРесурсы только у этого приложения
Откуда берётся jarКлиент загружает его на кластерОн уже лежит на classpath кластера, в папке usrlib
Командаflink run --target remoteflink run --target kubernetes-application

В нашем стенде режим Session, потому что кластер поднимает Docker Compose заранее. Развёртывание в Kubernetes разберём в уроке 20. Учти одну тонкость стенда. Команда docker compose exec jobmanager flink run выполняется в контейнере JobManager, но клиент при этом отдельная JVM. Твой main работает в ней, и JobManager его кода не исполняет.

В исходниках

В режиме Application задание подаётся изнутри кластера. Исполнитель обращается к Dispatcher напрямую, минуя REST, а в остальном передаёт тот же StreamGraph.
