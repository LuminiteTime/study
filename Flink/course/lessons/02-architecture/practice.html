Что будет в конце

В задании появится оператор посередине, у всех операторов будут постоянные идентификаторы, скрипт отправки избавит от длинной команды, и ты увидишь цепочку в выводе CLI и REST. Новых зависимостей нет. Файл scripts/cluster-status.sh из снапшота относится к заданию этого урока, пока его создавать не нужно.

Шаг 1. Дай операторам имена и uid

Открой src/main/java/dev/study/payguard/job/PayGuardJob.java и внеси такие правки.

ПРОСТЫМИ СЛОВАМИ

Источник получает имя payments-raw третьим аргументом и такой же uid. Имя видит человек в интерфейсе. По uid Flink находит состояние оператора при восстановлении.

Фильтр выбрасывает пустые строки. Настоящей очисткой мы займёмся в уроке 3. Сейчас он нужен, чтобы посередине появился оператор и стала видна цепочка.

name и uid относятся к предыдущему вызову, поэтому стоят сразу за фильтром.

Приёмник print тоже получает имя и uid. Состояния у него нет, зато правило «у каждого оператора есть uid» проще проверять.

getExecutionPlan возвращает план в JSON, и мы печатаем его в стандартный вывод. Это выполняется в main, поэтому строка появится в терминале клиента.

execute отправляет задание, как и раньше.

В исходниках

Зачем ставить uid сейчас, если состояния ещё нет. Посмотри, как Flink выбирает идентификатор оператора. Без uid хеш строится из положения узла в графе, а с uid только из этой строки.

Автоматический хеш зависит от структуры программы, поэтому добавленный фильтр может поменять идентификаторы соседей, и состояние из savepoint им больше не подойдёт. Документация настойчиво советует задавать uid вручную. Восстановление из savepoint мы разберём в уроке 13, и к тому времени uid уже должны стоять во всех версиях задания.

И почему печать плана не ломает запуск. Метод вызывает getStreamGraph(false), то есть не очищает список преобразований, и последующий execute их видит.

Документация: Savepoints, Assigning Operator IDs

Шаг 2. Скрипт отправки

Создай scripts/submit.sh.

Строка set -euo pipefail останавливает скрипт при первой ошибке и при обращении к неопределённой переменной. Флаг -T у docker compose exec отключает псевдотерминал, без него скрипт падал бы в CI, где терминала нет. Флаг --detached завершает клиента сразу после отправки. Конструкция "$@" передаёт аргументы скрипта после пути к jar, поэтому они попадают в main твоего задания. Флаги самого flink run, например -p, таким способом не передать, их пиши в отдельной команде.

chmod +x scripts/submit.sh

Команда chmod +x разрешает запускать файл как программу.

Шаг 3. Собери и отправь

Если стенд остался работать с урока 1, сначала выполни docker compose down, чтобы старое задание не занимало слоты. Порядок прежний, сначала сборка, потом Compose.

./gradlew shadowJar
docker compose up -d --wait
curl -s localhost:8081/overview | jq -c .
./scripts/submit.sh

В прогоне jar занял 24327017 байт. Ответ /overview подтверждает, что свободны все четыре слота. Поля те же, что в уроке 1.

Это StreamGraph, три узла с нашими именами. Поле ship_strategy показывает способ передачи между операторами. Значение FORWARD здесь значит, что подзадача передаёт записи подзадаче с тем же номером, и именно оно разрешает склейку. Значение parallelism равно 2, потому что в Compose задано parallelism.default: 2. Последняя строка содержит идентификатор задания, он пригодится в следующих командах.

Шаг 4. Посмотри на то, что реально работает

Спроси у REST, какие вершины запущены. Подставь свой идентификатор. Фильтр jq оставляет только нужные поля, а флаг -c печатает результат в одну строку.

curl -s localhost:8081/jobs/8fe3d0eda0de9f053bb73d644c2fd485 \
  | jq -c '{name, state, vertices: [.vertices[] | {name, parallelism, status}]}'
{"name":"payguard","state":"RUNNING","vertices":[{"name":"Source: payments-raw -> drop-blank -> Sink: stdout","parallelism":2,"status":"RUNNING"}]}

Три узла превратились в одну вершину с именем через стрелки. Это JobGraph, и склейку ты видишь своими глазами. Две подзадачи заняли два слота, значит в /overview теперь должно быть 2 в поле slots-available. При параллелизме 4 в нашем стенде заняты все четыре слота, это проверено на запуске из урока 13.

i
Как сравнивать цепочку и план

Вывод getExecutionPlan показывает логику до склейки, поэтому там всегда отдельные операторы. Настоящие вершины видны в ответе REST и на графе в Web UI. Если в плане FORWARD, а вершины разные, ищи различия в параллелизме или группе slot sharing.

Шаг 5. CLI

Список заданий кластера выдаёт команда flink list.

docker compose exec -T jobmanager flink list
Waiting for response...
------------------ Running/Restarting Jobs -------------------
07.11.2026 20:56:54 : 8fe3d0eda0de9f053bb73d644c2fd485 : payguard (RUNNING)
--------------------------------------------------------------
No scheduled jobs.

В строке стоят время запуска, идентификатор, имя из env.execute и статус. Остановить задание без сохранения состояния можно так.

docker compose exec -T jobmanager flink cancel 8fe3d0eda0de9f053bb73d644c2fd485

Команда cancel переводит задание в отменённое состояние, и все его вычисления прекращаются. После этого curl -s localhost:8081/jobs | jq -c . покажет задание со статусом CANCELED, а все четыре слота снова будут свободны. Для остановки с сохранением состояния есть flink stop, его мы разберём в уроке 13. Запусти задание снова командой ./scripts/submit.sh, идентификатор будет новым.

Шаг 6. Web UI

Открой http://localhost:8081. На странице запущенных заданий нажми payguard и найди на графе блок с надписью Source: payments-raw -> drop-blank -> Sink: stdout. Это та же одна вершина, что в REST. Нажми на неё и открой список подзадач, там их две, и у каждой указан TaskManager. На странице Task Managers видно число всех и свободных слотов. На странице задания есть вкладки Exceptions и Checkpoints. В нашем прогоне список исключений был пуст и чекпоинтов ноль, мы их ещё не включали.

Чтобы записи шли, запусти генератор из урока 1. Он отправит в поток битые записи, и они пока пройдут через фильтр дальше в print, потому что пустыми не являются.

./gradlew loadgen --args="--rate 5 --dup 0.02 --bad 0.01"

Шаг 7. Проверь на себе нехватку слотов

Этот опыт покажет, как выглядит авария из начала урока. Флаг -p задаёт параллелизм заданию при отправке и стоит перед путём к jar.

docker compose exec -T jobmanager flink cancel <id текущего задания>
docker compose exec -T jobmanager flink run --detached -p 8 /jobs/payguard-1.0.0.jar

В этом случае подзадач восемь, а слотов четыре. Вывод такого запуска мы не снимали, поэтому смотри на него сам и сверяй с теорией. Статус задания должен стать RUNNING, затем в логе JobManager появится NoResourceAvailableException. Если кластер только что поднят, ждать придётся до пяти минут. Логи можно читать командой docker compose logs jobmanager. Для продолжения курса верни обычный запуск через ./scripts/submit.sh.
