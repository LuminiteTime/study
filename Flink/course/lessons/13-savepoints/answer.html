Ответ

Библиотека ложится в implementation, то есть внутрь толстого jar. В дистрибутиве Flink её jar кладётся в opt/, так написано в flink-dist/src/main/assemblies/opt.xml. Из opt/ классы не загружаются, и с flinkProvided класс SavepointReader не нашёлся бы при запуске.

Сам инспектор.

ПРОСТЫМИ СЛОВАМИ

Берём путь к снимку из аргументов. getRequired сразу падает с понятной ошибкой, если аргумент забыли.

Обычное окружение DataStream в режиме BATCH. Снимок конечен, и программа должна завершиться, когда прочитает его до конца.

SavepointReader.read загружает метаданные снимка. Третий аргумент задаёт бэкенд, через который читается состояние. Задание пишет состояние в RocksDB, но снимок в формате canonical, а этот формат одинаков для всех бэкендов. Поэтому подходит лёгкий HashMapStateBackend.

readKeyedState строит поток по состоянию оператора с данным uid. Каждый ключ пройдёт через ProfileReader. executeAndCollect() без аргументов запускает программу и отдаёт итератор, который подтягивает результаты по мере готовности. try с ресурсами закрывает итератор и освобождает ресурсы кластера.

Печатаем число карт, потом сортируем по числу платежей по убыванию и берём первые пять.

Читатель ProfileReader устроен как обычная функция с состоянием. В open он регистрирует тот же дескриптор, что CardProfileFunction, а readKey вызывается по одному разу на каждый ключ в снимке. Собирать все карты в список допустимо, их тысячи. Для миллионов ключей сортировку стоило бы делать в самой программе Flink, а в клиент забирать только топ.

Инспектор тоже задание Flink, и ему нужен хотя бы один свободный слот. После шага 7 задание PayGuard занимает все 4 слота, поэтому сначала останови его со savepoint, прочитай этот снимок и верни задание командой из шага 7.

./gradlew shadowJar
SP=$(scripts/stop-with-savepoint.sh)
docker compose exec -T jobmanager flink run \
  -c dev.study.payguard.job.StateInspector \
  /jobs/payguard-1.0.0.jar --savepoint "$SP"

Флаг -c указывает класс с main, иначе CLI возьмёт PayGuardJob из манифеста. Флага --detached нет, клиент должен дождаться результатов. Метод main выполняется в клиенте, поэтому печать идёт прямо в терминал. Аргументы после jar достаются программе. Ниже вывод с нашего стенда после полутора минут генератора на 200 платежей в секунду. Ловушка executeAndCollect с лимитом

Первая версия инспектора вызывала executeAndCollect(Integer.MAX_VALUE). Казалось, что это значит «забери всё». Запуск упал раньше, чем прочиталась первая карта.

java.lang.OutOfMemoryError: Requested array size exceeds VM limit

В исходниках

Посмотри, что делает вариант с лимитом до того, как прочитать хотя бы одну запись.

Лимит уходит в начальную ёмкость ArrayList, и JVM пытается выделить массив на два миллиарда ссылок. Такой массив больше допустимого размера, отсюда ошибка. Вариант без аргументов возвращает CloseableIterator и ничего заранее не выделяет. Его комментарий требует закрыть итератор, чтобы освободить ресурсы кластера, поэтому он стоит в try с ресурсами.
