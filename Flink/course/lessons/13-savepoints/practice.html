Что будет в конце

В PayGuard появится оператор card-profile, который ведёт профиль каждой карты. Ты запустишь первую версию, остановишь задание со savepoint, добавишь в профиль поле и продолжишь с того же места. Потом ещё раз остановишь задание и запустишь его с параллелизмом 4. Файл StateInspector.java и зависимость flink-state-processor-api относятся к заданию, их пока создавать не нужно.

Шаг 1. Профиль карты, первая версия

Создай src/main/java/dev/study/payguard/model/CardProfile.java. Ниже состояние файла до правки. В снапшоте урока его нет, потому что на шаге 6 ты заменишь его второй версией.

package dev.study.payguard.model;

/** Накопленный профиль карты. Лежит в состоянии, поэтому менять его можно только по правилам эволюции схемы. */
public record CardProfile(long paymentCount, long totalAmountMinor) {

    public static final CardProfile EMPTY = new CardProfile(0, 0);

    public CardProfile plus(PaymentEvent payment) {
        return new CardProfile(paymentCount + 1, totalAmountMinor + payment.amountMinor());
    }
}

Record неизменяемый, поэтому метод plus возвращает новый профиль. Константа EMPTY избавляет функцию от проверок на пустое значение.

Шаг 2. Функция профиля

Создай src/main/java/dev/study/payguard/pipeline/CardProfileFunction.java. Этот файл не изменится во второй версии.

ПРОСТЫМИ СЛОВАМИ

Функция работает на потоке с ключом. Ключ это номер карты, на вход приходит платёж, на выход профиль.

Две публичные константы. UID станет надписью на коробке со состоянием оператора, STATE_NAME именем состояния внутри неё. Инспектор из задания прочитает снимок по этим же строкам, поэтому они вынесены в одно место.

Ссылка на состояние объявлена transient. Сама функция сериализуется при отправке на кластер, а состояние ей выдаёт среда выполнения в open.

Дескриптор описывает состояние именем и классом значения. По классу Flink строит PojoSerializer, и его снимок попадёт в savepoint вместе с данными.

На каждый платёж читаем профиль текущей карты. Для новой карты там null, и мы начинаем с EMPTY.

Записываем обновлённый профиль обратно и отдаём его дальше по потоку.

Шаг 3. Подключи оператор к заданию

Профили будут уходить в новый топик card.profiles. Добавь его имя в настройки задания.

В задании оператор встаёт на поток byCard, уже разбитый по карте. Тот же поток кормит правила, так что новый keyBy не нужен.

У оператора и у приёмника свои uid. Приёмник Kafka тоже хранит состояние, поэтому без uid он при следующей правке графа потерял бы его. Гарантия at-least-once здесь достаточна, повтор профиля после сбоя просто перезапишет то же значение у потребителя. Топик создаёт служба kafka-init, допиши его в список.

Шаг 5. Останови задание со savepoint

Создай scripts/stop-with-savepoint.sh и сделай его исполняемым.

Скрипт находит запущенное задание через REST и вызывает flink stop внутри контейнера JobManager. Флаг -T у docker compose exec отключает псевдотерминал, иначе в вывод попадут управляющие символы и grep не найдёт путь. Флаг --type canonical выбирает переносимый формат. Каталог снимка не передаём, его задаёт execution.checkpointing.savepoint-dir из docker-compose.yml. CLI печатает строку вида Savepoint completed. Path: ..., grep вырезает из неё путь, sed срезает точку в конце.

chmod +x scripts/stop-with-savepoint.sh
SP=$(scripts/stop-with-savepoint.sh)
echo "$SP"
file:/flink-data/savepoints/savepoint-1687c2-d2b5454c1f19

Имя каталога собрано из начала идентификатора задания и случайного суффикса. Путь указан изнутри контейнера. На твоей машине тот же каталог лежит в data/savepoints проекта, потому что ./data смонтирована в /flink-data. Внутри есть файл _metadata со списком операторов и снимками сериализаторов, рядом лежат файлы с данными состояния. Задание после команды перешло в FINISHED. Генератор продолжает писать в Kafka, и эти платежи никуда не денутся, новая версия начнёт читать со смещений, сохранённых в снимке.

Шаг 6. Вторая версия профиля

Замени CardProfile.java. В record появилось поле lastCountry, константа и метод plus его учитывают.

Поле добавлено в конец, но порядок здесь не важен. Сериализатор сопоставляет поля по имени, а перестановку аргументов конструктора берёт на себя JavaRecordBuilderFactory. Тип String ссылочный, поэтому у восстановленных профилей поле будет null, пока по карте не придёт новый платёж. Теперь добавь тест функции.

Тест прогоняет два платежа одной карты через harness из урока 7 и проверяет последний профиль. Страна DE берётся из фабрики тестовых платежей. На нашем стенде прошли все 40 тестов проекта.

./gradlew test shadowJar
docker compose exec -T jobmanager flink run --detached \
  --fromSavepoint "$SP" \
  /jobs/payguard-1.0.0.jar

Папка build/libs смонтирована в контейнер, поэтому новый jar виден сразу, пересоздавать контейнеры не нужно. Скрипт submit.sh здесь не подходит, он передаёт свои аргументы заданию, а флаг --fromSavepoint нужен самому CLI и должен стоять до пути к jar. Короткая форма флага -s. Если бы мы удалили оператор, сюда же добавился бы --allowNonRestoredState.

JOB=$(curl -s localhost:8081/jobs | jq -r '.jobs[] | select(.status == "RUNNING") | .id')
curl -s localhost:8081/jobs/$JOB/checkpoints | jq '.counts.restored, .latest.restored.external_path'

Первая команда покажет 1 восстановление и путь к снимку, вторая 0, то есть исключений не было. Так и было на нашем стенде, запуск второй версии из снимка первой прошёл без ошибок. Посмотри на сами профили.

С начала топика ты увидишь записи первой версии без поля страны. Записи второй версии выглядят так.

{"paymentCount":1,"totalAmountMinor":13896,"lastCountry":"ES"}
{"paymentCount":1,"totalAmountMinor":11869,"lastCountry":"PL"}

В записи нет номера карты, приёмник пишет только значение. Топик здесь служит следом работы оператора. Полную картину по картам даст инспектор из задания. Профиль уходит в топик после каждого платежа, поэтому lastCountry в топике всегда заполнено. Значение null живёт только в состоянии у карт, которые с момента релиза молчат.

Шаг 7. Смени параллелизм

SP=$(scripts/stop-with-savepoint.sh)
docker compose exec -T jobmanager flink run --detached -p 4 \
  --fromSavepoint "$SP" \
  /jobs/payguard-1.0.0.jar
curl -s localhost:8081/overview | jq '{slots: .["slots-total"], free: .["slots-available"]}'

Флаг -p 4 заменяет parallelism.default: 2 для всех операторов, у которых параллелизм не задан в коде. Все вершины получили по 4 подзадачи и уместились в 4 слота единственного TaskManager благодаря slot sharing из урока 2. На нашем стенде заняты все 4 слота из 4, задание поднялось из снимка без ошибок.

Состояние профилей было в двух подзадачах, с группами 0-63 и 64-127. Теперь диапазонов четыре, 0-31, 32-63, 64-95 и 96-127. Подзадачи 0 и 1 берут половины старой подзадачи 0, подзадачи 2 и 3 половины старой подзадачи 1. Это та же картина, что в симуляции на вкладке теории при 2 и 4. Значение maxParallelism мы не задавали, поэтому для параллелизма 4 планировщик и так вычислил 128, и спорить со снимком ему не пришлось.
