Релиз, который стирает память

Аналитики просят добавить в профиль карты страну последнего платежа. В коде это одно новое поле в record. Профиль хранится в состоянии задания, и за дни работы там накопились счётчики по тысячам карт. Если остановить задание командой cancel и запустить новый jar с чистого листа, профили начнутся с нуля. Вместе с ними пропадут дедупликация, открытые окна и частичные совпадения CEP.

Чекпоинт из урока 11 спасает от падений. Его создаёт и удаляет сам Flink, и рассчитан он на перезапуск того же кода. Для плановых изменений есть savepoint, снимок, который делаешь ты и который Flink никогда не удаляет сам. Сегодня мы разберём четыре вещи. Как savepoint находит оператор в новой версии программы. Какие правки типа состояния он переживает. Как состояние делится между другим числом подзадач. И как прочитать снимок без запуска задания.

Переезд с подписанными коробками

Переезжая, ты складываешь вещи в коробки и пишешь на каждой, в какую комнату её нести. Грузчики в новой квартире твоих вещей не знают и читают только надписи. Коробку с надписью «кабинет» поставят в кабинет. Если кабинета в новой квартире нет, грузчик остановится и спросит, что делать. Ответ «оставьте в кладовке, разберусь сам» и есть флаг --allowNonRestoredState.

Внутри каждой коробки лежит опись. Если в новом шкафу появилась лишняя полка, вещи по описи встанут на свои места, новая полка останется пустой. Если в описи написано «книги», а шкаф теперь ждёт обувь, вещи не встанут никуда. Книги ты заранее разложил по 128 пронумерованным коробкам по жёсткому правилу. В старой квартире было два стеллажа, в новой четыре. Коробки переставляют целиком, перекладывать книги не нужно. Число коробок поменять нельзя, оно определилось в день упаковки.

Во Flink надпись на коробке называется uid оператора, опись это снимок сериализатора, пронумерованные коробки это группы ключей (key groups), а стеллажи это подзадачи. Чекпоинт похож на вещи, разложенные по местам в той же квартире. После аварии их находят там, где оставили. Savepoint это коробки для переезда. Паковать их дольше, зато их можно везти в другую квартиру.

Чекпоинт и savepoint

Оба снимка создаются одним механизмом барьеров из урока 11. Отличаются они тем, кто ими владеет и для чего они нужны.

Формат canonical един для всех бэкендов состояния. Снимок, снятый с RocksDB, можно восстановить в HashMap и наоборот. Документация называет его самым стабильным форматом с наибольшей совместимостью между версиями и схемами. Формат native пишет то, что бэкенду удобно, у RocksDB это SST-файлы. Он быстрее создаётся и восстанавливается, но сменить бэкенд с ним нельзя. Эволюция схемы и чтение через State Processor API для него помечены в документации как работающие без гарантий.

Какой формат получится, если флаг --type не указан. Смотри на константу DEFAULT в конце перечисления.

По умолчанию снимается canonical. В нашем скрипте тип всё равно указан явно, чтобы через год никто не гадал, в каком формате лежат снимки.

В нашем docker-compose.yml с урока 11 стоит externalized-checkpoint-retention: RETAIN_ON_CANCELLATION, поэтому последние чекпоинты переживают и cancel. Запустить задание из такого чекпоинта тоже можно. Таблица в документации разрешает выровненному чекпоинту смену кода и параллелизма, а для эволюции схемы ставит знак «работает без гарантий». Для плановых релизов бери savepoint.

stop и cancel

Команда stop (flink stop) останавливает задание аккуратно. Источники получают просьбу отправить последний барьер, по нему снимается savepoint, и только после его успеха источники завершаются. Задание переходит в состояние FINISHED, CLI печатает путь к снимку. Команда cancel (flink cancel) останавливает задание сразу и savepoint не снимает. Старый флаг cancel --withSavepoint объявлен устаревшим, документация советует вместо него stop. Есть и третья команда, flink savepoint. Она снимает снимок и оставляет задание работать, так удобно получить копию состояния для анализа.

⚠
Флаг --drain нужен только при окончательной остановке

С флагом --drain перед последним барьером уходит MAX_WATERMARK. Все таймеры по времени события срабатывают, и минутные окна продавцов закроются досрочно с неполными суммами. Документация прямо предупреждает, что продолжение задания после такого снимка может дать неверные результаты. Для релиза используй stop без этого флага.

Как состояние находит свой оператор

Внутри savepoint лежит отображение «идентификатор оператора → состояние». Идентификатор (OperatorID) это 16 байт. Если у оператора задан uid, байты получаются хешем от этой строки. Если не задан, Flink выводит их из положения оператора в графе, и правка топологии может их сдвинуть. Об этом шла речь в уроке 2.

В исходниках

Как строка uid превращается в идентификатор при сборке графа. Хеш murmur3 на 128 бит от UTF-8 байтов строки, и больше ничего в него не входит.

State Processor API считает идентификатор той же функцией. Поэтому в задании урока достаточно передать строку card-profile, и инспектор найдёт состояние оператора в снимке.

Отсюда следует простое правило. Одинаковый uid в двух версиях программы даёт одинаковый идентификатор, и состояние находит оператор. Имя оператора, которое задаёт .name(), в этом не участвует.

При запуске из снимка JobManager сначала читает его метаданные и проверяет, что каждому сохранённому состоянию нашёлся оператор. Это делает метод Checkpoints.loadAndValidateCheckpoint.

В исходниках

Первый шаг. Для каждой вершины нового графа в таблицу кладутся оба идентификатора оператора, выведенный из графа и заданный через uid.

Второй шаг. Для состояния, которому оператор не нашёлся, есть три исхода. С флагом allowNonRestoredState оно пропускается с записью в лог. Без флага пустое состояние тоже пропускается. Непустое приводит к исключению.

Текст исключения задан чуть ниже в том же файле, в throwNonRestoredStateException. Он начинается словами Failed to rollback to checkpoint/savepoint и заканчивается советом поставить --allowNonRestoredState. В обратную сторону проверки нет. Новый оператор, которого не было в снимке, просто стартует с пустым состоянием.

Документация: Command-Line Interface, Starting a Job from a Savepoint

Флаг --allowNonRestoredState выбрасывает состояние насовсем. Ставь его, только когда оператор удалён намеренно. Если же ты случайно поменял uid, флаг тихо обнулит состояние оператора, и задание запустится как ни в чём не бывало. Правильное лечение в этом случае вернуть старый uid.

Эволюция схемы состояния

Значения состояния лежат в снимке байтами. Прочитать их может только сериализатор того же формата, поэтому рядом с данными Flink кладёт снимок сериализатора (serializer snapshot). Это описание формата, например список полей POJO с их типами. При восстановлении новый сериализатор сравнивает себя со старым снимком. Возможны четыре ответа. Совместим как есть. Совместим после миграции, тогда старые байты читаются старым сериализатором и переписываются новым. Совместим после перенастройки. Несовместим, тогда восстановление падает.

Для POJO документация задаёт правила.

  • Поля можно удалять. Старое значение удалённого поля пропадёт в следующих снимках.
  • Поля можно добавлять. Новое поле получит значение по умолчанию для своего типа в Java.
  • Тип объявленного поля менять нельзя.
  • Имя класса, включая пакет, менять нельзя.

Record во Flink 2.2 идёт тем же путём. TypeExtractor признаёт record типом POJO, даже без конструктора по умолчанию и сеттеров, и сериализует его через PojoSerializer. Наш CardProfile как раз record.

В исходниках

Проверка совместимости в PojoSerializerSnapshot.resolveSchemaCompatibility. Сначала сравнивается класс, потом сериализаторы полей, которые есть в обеих версиях.

Если класс и старые поля совпали, а набор полей изменился, ответ будет «совместим после миграции».

Каким станет новое поле record после миграции, решает JavaRecordBuilderFactory. Если имена или порядок компонент изменились, он строит таблицу перестановки аргументов конструктора. Новые примитивные поля получают значение по умолчанию, остальные новые поля остаются null.

Для нашего релиза это значит следующее. Профили, восстановленные из старого снимка, получат lastCountry == null и будут жить так до первого нового платежа по карте. Код, который читает это поле, обязан пережить null.

💡
Переименование поля равно удалению и добавлению

Поля сопоставляются по имени. Если переименовать totalAmountMinor в totalMinor, Flink увидит удалённое поле и новое. Задание запустится без единой ошибки, а суммы всех карт станут нулём. Тесты на harness это не поймают, потому что в них один и тот же класс с обеих сторон, об этом урок 16.

Ещё три ограничения из той же страницы документации. Ключ состояния эволюционировать не может, его байты служат адресом, и у RocksDB сравниваются побайтно. Типы, которые ушли в Kryo, эволюции не поддерживают вовсе. Наше задание с урока 3 запрещает Kryo настройкой pipeline.generic-types: false, поэтому для такого типа Flink откажется создавать сериализатор и задание упадёт сразу, до первого снимка. Если правка всё-таки несовместима, остаются свой сериализатор или переписывание снимка через State Processor API.

Rescale через группы ключей

В уроке 4 мы считали, куда попадает ключ. Номер группы равен murmurHash(key.hashCode()) % maxParallelism и от параллелизма не зависит. Подзадача владеет непрерывным диапазоном групп. Теперь посмотрим на тот же механизм со стороны восстановления. Состояние в снимке разложено по группам, и при смене параллелизма Flink переносит его целыми группами. Такой запуск с другим параллелизмом называют rescale.

Восстановление с другим параллелизмом

Поставь 2 и 4 при 128 группах. Сменят владельца 96 групп, при этом каждая новая подзадача читает кусок ровно одной старой. Поставь 2 и 3, и средняя подзадача соберёт своё состояние из двух старых. Выбери 4 группы и параллелизм 6, чтобы увидеть отказ.

В исходниках

Раскладкой состояния при восстановлении занимается StateAssignmentOperation. Если параллелизм не изменился, подзадача получает файлы своей прежней подзадачи как есть. Иначе для неё собираются пересечения со всеми старыми файлами.

Диапазоны для нового параллелизма нарезаются той же функцией, что используется при обработке записей.

Комментарий к createKeyGroupPartitions требует, чтобы эта нарезка совпадала с KeyGroupStreamPartitioner. Иначе запись пришла бы в подзадачу, у которой нет состояния её ключа. Формулы диапазона и computeOperatorIndexForKeyGroup из урока 4 согласованы, и симуляция выше считает по ним обеим.

Состояние без ключа (operator state), например список назначенных источнику партиций Kafka, на группы не делится. В том же методе его раздаёт по кругу RoundRobinOperatorStateRepartitioner.

Предел, заданный при первом запуске

Число групп, оно же максимальный параллелизм (maxParallelism), записано в снимке у каждого оператора. При восстановлении оно сверяется с новым графом дважды.

В исходниках

Первая проверка. Подзадач не может быть больше, чем групп в снимке.

Вторая проверка касается самого числа групп. Если ты его не задавал, планировщик вычислил значение сам и пометил его как автоматическое. Такое значение разрешено заменить числом из снимка. Заданное явно заменить нельзя.

Наш проект maxParallelism не задаёт, поэтому новое задание молча примет 128 групп из снимка, даже если по формуле из урока 4 для нового параллелизма вышло бы 256. Если же в новой версии появится env.setMaxParallelism(1024) при снимке со 128 группами, loadAndValidateCheckpoint бросит исключение с текстом Max parallelism mismatch between checkpoint/savepoint state and new program. Сменить число групп у работающего состояния можно только переписав снимок через State Processor API.

Сравнение со Spark

В Spark Structured Streaming состояние живёт в checkpoint location конкретного запроса. Оно разбито на spark.sql.shuffle.partitions частей, и это число нельзя менять после первого запуска. Список изменений запроса, с которыми можно продолжить с того же каталога, задан в документации Spark, и смена ключей или агрегатов stateful-операции туда не входит.

У Flink снимок отделён от программы и привязан к операторам через uid. Параллелизм меняется при каждом запуске в пределах числа групп. Тип состояния может эволюционировать по правилам сериализатора, а всё остальное можно переписать отдельной пакетной программой.

Снимок как база данных

Документация State Processor API предлагает смотреть на savepoint как на базу данных. Каждый uid служит отдельной схемой. Состояние с ключом одного оператора превращается в таблицу, где одна колонка хранит ключ и по колонке приходится на каждое состояние. Читать такую базу можно обычной программой DataStream в режиме BATCH. Тем же API можно записать новый снимок, например заполнить состояние из истории до первого запуска, сменить uid или число групп. В задании урока ты напишешь инспектор, который печатает самые активные карты прямо из снимка. Запущенное задание ему не нужно.
