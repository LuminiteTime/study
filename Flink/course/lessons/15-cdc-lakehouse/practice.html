Что будет в конце

На стенде работают два кластера, основной на порту 8081 и SQL на порту 8082. Изменение строки в merchants появляется в топике merchants.changelog, а алерты складываются в таблицу Paimon на диске. Файл задания мы пока не создаём, он появится на вкладке «Задание». Файл build.gradle.kts в этом уроке не меняется, потому что новые коннекторы лежат в образе SQL-кластера и в jar не попадают.

Шаг 1. Добавь коннекторы в образ

Открой docker/Dockerfile из урока 14 и допиши три файла в /opt/flink/lib.

ПРОСТЫМИ СЛОВАМИ

Толстый jar коннектора postgres-cdc. Версия 3.7.0-2.2 читается как версия Flink CDC плюс версия Flink, под которую он собран.

Коннектор и каталог Paimon. Сборка привязана к Flink 2.2 через имя артефакта paimon-flink-2.2, а 2.1.0 это уже версия самого Paimon.

Комментарий объясняет следующую строку. Склад у нас на локальном диске, но классы Hadoop всё равно нужны.

Сборка Hadoop от проекта Flink, все классы в одном jar.

Мы проверили, что будет без последней строки. Paimon падает с такой ошибкой.

java.lang.ClassNotFoundException: org.apache.hadoop.conf.Configuration

Шаг 2. Настрой PostgreSQL и Kafka

В docker-compose.yml меняются две службы.

В kafka-init появляется топик merchants.changelog. Флаг --config cleanup.policy=compact делает его компактируемым, поэтому он создаётся отдельной командой вне общего цикла. В postgres строка command запускает сервер с wal_level=logical. Этот параметр читается только при старте сервера, поэтому он задан в аргументах запуска.

Шаг 3. Включи REPLICA IDENTITY

Строка стоит сразу после создания таблицы. Если её забыть, снимок прочитается нормально, топик заполнится, и всё будет выглядеть рабочим до первого UPDATE. После него задание уходит в цикл RESTARTING.

java.lang.IllegalStateException: The "before" field of UPDATE/DELETE message is null, please check the Postgres table has been set REPLICA IDENTITY to FULL level.

Лечение в уже работающей системе требует порядка, потому что плохая запись осталась в журнале, а слот будет отдавать её снова. Сначала отмени задание, удали слот, выполни ALTER TABLE merchants REPLICA IDENTITY FULL и запусти задание заново со снимка. Повторный снимок топику не вредит, у каждой строки тот же ключ.

Шаг 4. Собери и подними стенд

Команды выполняй именно в таком порядке.

./gradlew shadowJar
docker compose --profile sql down -v
docker compose --profile sql up -d --wait --build

Сборка идёт первой, иначе Docker смонтирует пустую build/libs, и jar в контейнере не появится. На этом мы реально споткнулись.

Флаг -v у down удаляет анонимные тома контейнеров. Это важно для PostgreSQL, потому что образ выполняет init.sql только на пустом каталоге данных, и старая база осталась бы без новой строки ALTER TABLE. Папка ./data смонтирована как обычный каталог и при этом не удаляется. Флаг --build заставляет пересобрать образ. Без него Compose увидит готовый payguard-flink-sql:2.2.1 из урока 14 и новых коннекторов в кластере не будет. Флаг --profile sql включает службы SQL-кластера, ты уже знаешь его по уроку 14.

Шаг 5. Запусти CDC

Создай sql/cdc_merchants.sql.

ПРОСТЫМИ СЛОВАМИ

Строка connector выбирает коннектор, следующие строки говорят, куда подключаться и под каким пользователем. Значения совпадают с настройками службы postgres в Compose.

База, схема и таблица, которые мы читаем.

Имя слота на сервере. Обязательная настройка, и каждому заданию нужно своё имя.

Режим снимка по чанкам. По умолчанию выключен.

Плагин декодирования. Значение по умолчанию decoderbufs должно быть установлено на сервере, мы его не ставим и берём стандартный pgoutput.

Таблица-приёмник в строках 23-33 содержит PRIMARY KEY, он станет ключом сообщения. Колонку updated_at мы намеренно не переносим. Формат JSON указан отдельно для ключа и для значения. Отправь задание на SQL-кластер.

docker compose --profile sql exec -T sql-jobmanager sql-client.sh -f /sql/cdc_merchants.sql

Флаг -f выполняет файл целиком, флаг -T у exec отключает псевдотерминал, в скрипте он не нужен. Клиент отправит INSERT и завершится, а задание останется работать на кластере, потому что по умолчанию DML выполняется асинхронно.

В исходниках

Значение по умолчанию у настройки table.dml-sync равно false, описание говорит об асинхронном запуске. Именно поэтому терминал вернётся сразу.

Документация: SQL Client

Посмотри на слот со стороны базы.

docker compose exec postgres psql -U payguard -d payguard -c "SELECT slot_name, plugin, active, restart_lsn, confirmed_flush_lsn, wal_status, pg_size_pretty(pg_wal_lsn_diff(pg_current_wal_lsn(), restart_lsn)) AS retained FROM pg_replication_slots;"

Должна быть строка payguard_merchants с плагином pgoutput и active, равным t. Колонка retained показывает, сколько журнала удерживает слот, разницу считает pg_wal_lsn_diff. Этот же запрос подойдёт для алерта. В момент снимка рядом могут появиться временные слоты с суффиксами _0 и _1.

Шаг 6. Поменяй строку и прочитай топик

docker compose exec postgres psql -U payguard -d payguard \
  -c "update merchants set risk_level='HIGH' where merchant_id='m-0007'"

docker compose exec -T kafka /opt/kafka/bin/kafka-console-consumer.sh \
  --bootstrap-server localhost:9092 --topic merchants.changelog --from-beginning \
  --formatter-property print.key=true --timeout-ms 10000 2>/dev/null | grep m-0007

Настройка print.key=true велит печатать ключ перед значением через табуляцию, а --timeout-ms завершает чтение, когда новых записей нет 10 с. Изменение появилось в топике.

{"merchant_id":"m-0007"}	{"merchant_id":"m-0007","risk_level":"HIGH"}

Слева ключ, справа значение. Рядом с этой строкой лежит прежняя с LOW, она из снимка. Компактирование её пока не убрало, потому что активный сегмент не компактируется. Для потребителя это безопасно, последняя запись по ключу побеждает.

Посчитай записи, заменив grep m-0007 на wc -l. На чистом стенде мы получили 50 записей сразу после снимка, по одной на продавца из init.sql, и 51 после одного UPDATE. Повторяется по ключу только m-0007. В первом, отладочном прогоне вышло 52. Там строку меняли и до включения REPLICA IDENTITY FULL, и после него, и лишняя запись скорее всего осталась от той отладки. Приёмник по умолчанию даёт гарантию at-least-once, а повтор по тому же ключу компактируемому топику не вредит.

Шаг 7. Сложи алерты в озеро

Создай sql/paimon_alerts.sql.

ПРОСТЫМИ СЛОВАМИ

Каталог Paimon. warehouse это корневая папка всех таблиц. Она лежит на томе ./data, который виден и JobManager, и TaskManager. В проде здесь был бы адрес объектного хранилища.

Таблица создаётся в каталоге и переживает перезапуск клиента, поэтому IF NOT EXISTS позволяет запускать файл повторно.

Обычные колонки алерта и день события, по которому мы партиционируем.

В первичный ключ входит колонка партиции, поэтому строка не может переехать в другую партицию, и особый режим cross partition upsert не нужен. Повтор alert_id в пределах дня схлопнется в одну строку.

Два фиксированных бакета в каждой партиции. changelog-producer = input велит считать входной поток полным changelog и писать его в отдельные файлы для потоковых читателей. У нас вход состоит из вставок, поэтому никаких затрат на вычисление старых значений нет.

Таблица alerts_topic объявлена как TEMPORARY, поэтому живёт только в сессии и не записывается в каталог Paimon. Настройка properties.isolation.level = read_committed нужна, чтобы не читать незафиксированные алерты, разницу мы измерили в уроке 12.

Запусти основное задание, задание озера и генератор с редкими сериями. Генератор занимает терминал, поэтому он идёт последним.

scripts/submit.sh
docker compose --profile sql exec -T sql-jobmanager sql-client.sh -f /sql/paimon_alerts.sql
./gradlew loadgen --args="--rate 100 --burst 0.001 --card-testing 0.002"

Флаги --burst и --card-testing задают доли платежей, из которых вырастают серии для правил velocity и card-testing. Через пару чекпоинтов посмотри на папку таблицы из второго терминала.

ls -F data/lake/default.db/fraud_alerts
event_day=2026-11-07/ manifest/ schema/ snapshot/

Имя партиции у тебя будет с другой датой. Внутри неё лежат bucket-0 и bucket-1 с файлами data-*.parquet и changelog-*.parquet. Файл snapshot/LATEST хранит номер последнего снимка. Открой файл снимка с этим номером, это JSON, поля totalRecordCount и deltaRecordCount показывают, сколько записей в таблице и сколько добавил этот коммит.

Шаг 8. Убери слот за собой

Когда закончишь эксперименты, отмени задание CDC и удали слот. Команда flink list покажет идентификатор задания. Слот с подключённым получателем удалить нельзя, поэтому порядок такой.

docker compose --profile sql exec -T sql-jobmanager flink list
docker compose --profile sql exec -T sql-jobmanager flink cancel <job-id>
docker compose exec postgres psql -U payguard -d payguard \
  -c "SELECT pg_drop_replication_slot('payguard_merchants');"

Документация: pg_drop_replication_slot, DROP_REPLICATION_SLOT
