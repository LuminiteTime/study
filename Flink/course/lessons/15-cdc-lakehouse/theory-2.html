REPLICA IDENTITY и поле before

Настройка таблицы REPLICA IDENTITY решает, какие старые значения PostgreSQL кладёт в журнал при UPDATE и DELETE.

ЗначениеЧто попадает в журнал
DEFAULTСтарые значения колонок первичного ключа. Режим по умолчанию для обычных таблиц
USING INDEXСтарые значения колонок указанного уникального индекса
FULLСтарые значения всех колонок строки
NOTHINGНичего про старую строку

Документация добавляет важную оговорку. Обычно старое значение колонки пишется, только если оно отличается от нового. Первичный ключ при смене уровня риска не меняется, поэтому в режиме DEFAULT старой строки в журнале нет совсем. А коннектору в режиме changelog-mode = all она нужна, потому что он обязан выдать пару записей -U и +U.

В исходниках

Посмотрим, как событие Debezium превращается в строки Flink. Записи снимка приходят с операцией READ и становятся INSERT. На обновление в режиме ALL сначала извлекается поле before, и оно сразу уходит в проверку.

Проверка для PostgreSQL падает с исключением на пустой строке. Текст исключения это и есть та ошибка, которую ты увидишь в логе.

Условие changelogMode == ALL показывает и запасной выход. Если FULL на таблице включить нельзя, у коннектора есть changelog-mode = upsert, в котором поле before не запрашивается. Этому режиму нужен первичный ключ. Наш курс использует FULL, а его цена следует из определения выше, на каждое обновление в журнал пишется вся старая строка.

Документация: ALTER TABLE, REPLICA IDENTITY, changelog-mode

Upsert-kafka и компактируемый топик

Коннектор upsert-kafka пишет changelog в Kafka с такой логикой. Первичный ключ таблицы становится ключом сообщения Kafka, новая версия строки становится значением, а удаление превращается в сообщение с пустым значением (tombstone). Все изменения одного ключа попадают в одну партицию, поэтому их порядок сохраняется.

Топик с настройкой cleanup.policy=compact хранит для каждого ключа как минимум последнее значение, старые версии брокер со временем вычищает. Такой топик работает как таблица. Новый потребитель читает его с начала и получает весь справочник без обращения к PostgreSQL. Компактирование не трогает активный сегмент, поэтому только что записанные версии какое-то время лежат рядом, и ты увидишь это в практике.

В исходниках

Без первичного ключа таблица не создастся, потому что ключ сообщения брать неоткуда. Сразу под этой проверкой в файле объявлен режим приёмника. В нём нет UPDATE_BEFORE, поэтому на один UPDATE в базе в топик уходит одна запись.

Сериализация показывает, как рождается tombstone. Для DELETE и UPDATE_BEFORE значение становится null, остальные записи пишутся как обычные INSERT, чтобы их принял формат вроде JSON, понимающий только вставки. До ветки с UPDATE_BEFORE наши записи не доходят, потому что режим приёмника таких строк не объявляет. Это видно и в замере из практики, один UPDATE дал одну запись без tombstone.

Документация: Upsert Kafka, Kafka, Log Compaction

Lakehouse и Paimon

Алерты в Kafka нужны для реакции, а аналитикам нужен SQL по истории за месяцы. Lakehouse закрывает это файлами в дешёвом хранилище, поверх которых лежат метаданные таблицы. Метаданные дают то, чего нет у папки с Parquet, это атомарную публикацию изменений и обновление строк по ключу. Apache Paimon как раз такой формат таблиц, и читать его можно разными движками, в том числе Spark.

Устройство таблицы с первичным ключом удобно смотреть сверху вниз. Партиция делит данные по значению колонки, у нас по дню. Внутри партиции бакеты, каждый со своим LSM-деревом (log-structured merge-tree). Писатель накапливает записи, сортирует их и сбрасывает новым файлом, а compaction потом сливает файлы, чтобы чтению не приходилось перебирать много версий одного ключа.

Изменения становятся видимыми, когда опубликован снимок таблицы. Снимок ссылается на схему и списки манифестов, а манифесты перечисляют живые файлы. Потоковая запись публикует изменения на чекпоинтах Flink, поэтому документация Paimon требует их включить. Интервал чекпоинта у нас 15 с, значит, столько же примерно ждать свежих алертов в отчёте.

Механизм слияния (merge engine) задаёт, как записи с одним ключом складываются в одну логическую строку. По умолчанию это deduplicate, он оставляет последнюю. Идентификатор нашего алерта детерминирован, он собран из правила и платежа, поэтому повторная обработка даёт тот же ключ, и строка останется одна.

Настройка bucket выбирает режим распределения. Положительное число включает фиксированные бакеты, номер считается как хеш ключа бакета по модулю их числа. Без настройки таблица работает с динамическими бакетами (-1), и тогда в одну партицию может писать только одно задание. Ключом бакета по умолчанию служит первичный ключ без колонок партиции, поэтому при ключе (event_day, alert_id) хеш считается от alert_id.

Три разных снимка в одном уроке

Чекпоинт Flink это снимок состояния задания. Снимок CDC это начальное чтение таблицы PostgreSQL. Снимок Paimon это опубликованная версия таблицы, файл snapshot/snapshot-N. Связь между ними одна, публикация снимка Paimon при потоковой записи привязана к чекпоинту Flink.

Почему Paimon в этом курсе

Документация Paimon называет таблицы с первичным ключом основным инструментом для CDC и upsert-потоков, а сборка paimon-flink-2.2 версии 2.1.0 проверена на нашем стенде. Рантайм Iceberg под Flink 2.2 появился только в Iceberg 1.12.0, линия 1.11.0 заканчивалась на Flink 2.1, и на стенде курса Iceberg не запускался.

Та же таблица в пакетном режиме

Писатель работает непрерывно, а читателю это не мешает. Запрос в режиме execution.runtime-mode = batch читает один снимок и завершается, писатель в этот момент продолжает работать. Повтори запрос, и он прочитает снимок поновее. Тот же SELECT в режиме streaming сначала прочитает текущее содержимое, потом продолжит следить за изменениями и сам не завершится. Для запроса к старой версии есть подсказка /*+ OPTIONS('scan.snapshot-id' = '1') */, это чтение в прошлое (time travel).
