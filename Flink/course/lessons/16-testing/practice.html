Что будет в конце

В проекте появятся проверка графа, restore-тест, сквозной тест на настоящих Kafka и PostgreSQL, отдельная задача Gradle для него и файл CI. Итог прогона на нашем стенде был такой. Обычных тестов 45, вместе с тестом из задания, и все зелёные. Сквозной тест занял 7 с. Файл GitHub Actions мы не запускали ни разу, поэтому считай его проверенным только глазами.

Файл решения задания DeduplicateRestoreTest.java пока создавать не нужно. Без него обычных тестов будет на один меньше.

Шаг 1. Отдели описание графа от запуска

Весь граф был описан прямо в main и там же запускался. Тест такой метод вызвать не сможет, потому что env.execute начнёт работу. В PayGuardJob.java разделим его на три метода.

ПРОСТЫМИ СЛОВАМИ

main теперь занимает три строки. Он создаёт окружение, описывает граф и запускает его. Поведение на кластере осталось прежним.

createEnvironment хранит запрет на Kryo. Тесты вызовут именно его и получат те же условия, что и прод. Если написать в тесте свой getExecutionEnvironment, запрет потеряется молча.

GENERIC_TYPES со значением false это настройка pipeline.generic-types из урока 3.

buildPipeline только описывает граф. Он ничего не исполняет и принимает окружение снаружи, поэтому тест топологии и E2E вызовут его со своим окружением.

Шаг 2. Настройки базы, доступные из теста

Настройки PostgreSQL читались прямо из System.getenv. Поменять переменные окружения работающей JVM из Java-кода нельзя, а адрес базы в контейнере Testcontainers становится известен только после запуска контейнера. MiniCluster работает в той же JVM, что и тест, поэтому подойдут системные свойства. Создай в пакете job новый файл.

Сначала читается переменная окружения, и на кластере ничего не меняется. Если её нет, берётся системное свойство. Теперь замени прямые вызовы в двух местах.

Шаг 3. Тест топологии

Создай src/test/java/dev/study/payguard/job/PipelineTopologyTest.java.

ПРОСТЫМИ СЛОВАМИ

Граф строится один раз на весь класс, тесты только смотрят на него.

Заглушки настроек нужны потому, что JDBC-приёмник читает настройки уже при описании графа, а конструктор JdbcConnectionOptions не принимает пустой адрес. Соединения с unused никто не открывает.

Окружение и граф берутся из тех же методов, что и в проде. Адрес Kafka остаётся значением по умолчанию, его тоже никто не использует.

getStreamGraph превращает описание в граф узлов. Если функция несериализуема, тест упадёт ещё раньше, в buildPipeline, и упадёт весь класс.

Первый тест собирает имена всех узлов без uid и требует пустой список. Сообщение AssertJ сразу называет виноватых.

Тесты uidsAreUnique и graphTranslatesToJobGraph проверяют, что идентификаторы не повторяются и что граф переводится в JobGraph. Запусти только этот класс.

./gradlew test --tests '*PipelineTopologyTest'

Флаг --tests отбирает тесты по шаблону имени. Кавычки нужны, чтобы оболочка не раскрыла звёздочку сама. Теперь проверь, что тест умеет падать, потому что тест, который никогда не падает, ничего не доказывает. Мы сделали две поломки на копии снапшота, повтори их и верни код обратно.

  • Убери .uid("dlq-sink") в PayGuardJob. Упадут everyOperatorHasStableUid и uidsAreUnique. Первый назовёт сразу два узла, dlq-sink: Writer и dlq-sink: Committer, потому что один вызов sinkTo разворачивается в два оператора. Второй увидит в списке повторяющийся null.
  • Убери implements Serializable у RuleConfig. Класс упадёт с тем же сообщением, что и flink run из урока 8. Тест DynamicRulesTest на harness при этом останется зелёным.

Шаг 4. Restore-тест

Создай src/test/java/dev/study/payguard/pipeline/CardProfileRestoreTest.java.

ПРОСТЫМИ СЛОВАМИ

Первый harness играет задание до падения. open создаёт состояние, и два платежа копятся в профиле карты c1.

snapshot снимает состояние. Аргументы это номер чекпоинта и его время, сами значения на результат здесь не влияют. После закрытия первого harness снимок остаётся живым.

Второй harness это задание после рестарта. initializeState вызывается строго до open, иначе harness бросит исключение, в исходниках эта проверка стоит первой.

Третий платёж и проверка. Значения 3 платежа и 700 единиц получаются, только если первые два платежа пережили рестарт. extractOutputValues вернёт выход только нового экземпляра, поэтому в нём один элемент.

Настоящий KeyedProcessOperator оборачивает функцию, и harness получает селектор ключа. Метод вынесен отдельно, чтобы оба экземпляра были созданы одинаково.

Проверь и его поломкой. Замени в CardProfileFunction состояние обычным полем. На копии снапшота CardProfileFunctionTest остался зелёным, а этот тест упал и показал профиль из одного платежа на 400 единиц. Именно такую ошибку он и должен ловить.

Шаг 5. Отдельная задача Gradle для E2E

Контейнеры не должны запускаться при каждом ./gradlew test. Сквозной тест помечается тегом JUnit, и две задачи выбирают тесты по этому тегу.

ПРОСТЫМИ СЛОВАМИ

platform подключает BOM, файл с согласованными версиями библиотек Testcontainers. Поэтому у трёх модулей ниже версия не указана.

Обычная задача test выбрасывает всё, что помечено тегом e2e.

Своей задаче типа Test надо явно сказать, где лежат скомпилированные тесты и какой classpath брать. Значения те же, что у обычных тестов.

includeTags оставляет только сквозные тесты. shouldRunAfter просит запускать их после обычных, если в одной команде указаны обе задачи, и зависимости между ними не создаёт.

Блок про commons-lang3 в конце этого diff разберём в шаге 7, это следствие настоящего расследования. В комментарии к задаче стоит оценка «минуты», на нашем стенде тест занял 7 с. При первом запуске добавится скачивание образов.

Шаг 6. Сквозной тест

Создай src/test/java/dev/study/payguard/job/PayGuardE2ETest.java.

ПРОСТЫМИ СЛОВАМИ

@Tag("e2e") связывает класс с задачей из шага 5. @Testcontainers сам запустит и остановит поля с аннотацией @Container.

Образы заданы точно, как и везде в курсе. PostgreSQL получает при старте тот же sql/init.sql, что и стенд Compose, поэтому схема и справочник продавцов настоящие.

MiniCluster с одним TaskManager на 8 слотов. Этого хватает на весь граф при параллелизме 2.

Адрес базы становится известен только после старта контейнера. Он уходит в системные свойства, которые прочитает DbSettings.

Топики создаются заранее, по две партиции на каждый.

ПРОСТЫМИ СЛОВАМИ

Настоящий граф через настоящую фабрику. Чекпоинты каждую секунду нужны, чтобы транзакция с алертами фиксировалась быстро. Аргумент --bootstrap читает JobConfig, так задание получает адрес Kafka из контейнера.

executeAsync запускает задание и сразу возвращает управление. Обычный execute ждал бы конца потока, которого нет.

Потребитель читает алерты и DLQ. В newConsumer задан read_committed, поэтому он увидит только зафиксированные транзакции. Так тест проверяет, что транзакция с алертом действительно фиксируется.

Источник читает с конца топика и стартует не сразу. Одна посылка могла бы пропасть, поэтому пачка отправляется в цикле, пока не появится результат или не выйдет дедлайн в две минуты.

Проверяем три вещи сразу. Правило velocity сработало, потому что в пачке 12 платежей по карте при пороге 10. Обогащение сходило в настоящую базу и принесло HIGH для m-0000, так задано в init.sql. Битая запись попала в DLQ.

job.cancel в finally останавливает задание, даже если проверка упала.

Docker должен быть запущен. Поднимать стенд из Compose не нужно, контейнеры тест создаёт себе сам.

./gradlew test
./gradlew e2eTest

Первая команда идёт без Docker. Результаты смотри в build/reports/tests/test/index.html и build/reports/tests/e2eTest/index.html. На нашем стенде это 45 тестов в первом отчёте, вместе с тестом из задания, и один сквозной за 7 с во втором.

Шаг 7. Как мы нашли проблему с commons-lang3

Этот шаг про диагностику. При первом запуске сквозной тест повис на 60 с и упал так.

Timed out waiting for log output matching '.*Transitioning from RECOVERY to RUNNING.*'

Сообщение наводит на мысль о медленной Kafka. Но логов контейнера не было совсем. Значит, Kafka внутри него даже не начала запускаться. Такая подсказка важнее текста ошибки, поэтому мы пошли смотреть, что происходит в самом тесте. В стандартном потоке ошибок лежала строка, которую легко было пропустить. В HTML-отчёте Gradle такой поток показан у класса теста отдельно.

Exception in thread "Thread-6" java.lang.NoSuchMethodError: 'java.lang.String org.apache.commons.lang3.SystemProperties.getUserName(java.lang.String)'

Причина оказалась вот в чём. Testcontainers копирует скрипт старта в контейнер Kafka tar-архивом, который пакует в отдельном потоке. Этот поток вызвал метод commons-lang3 и умер, потому что такого метода не нашлось. Docker получил пустой архив и ответил 200, скрипт старта в контейнере не появился. Сам тест об этом не узнал и 60 с честно ждал строку в логе.

Откуда взялась старая версия. Библиотека openlineage-sql-java-1.32.0.jar содержит внутри себя копию commons-lang3 и стоит раньше на classpath. В проект она приходит транзитивно, из JDBC-коннектора. Проверить оба факта можно самому.

./gradlew dependencyInsight --dependency openlineage-sql-java --configuration testRuntimeClasspath
find ~/.gradle/caches/modules-2/files-2.1/io.openlineage -name 'openlineage-sql-java-1.32.0.jar' \
  -exec unzip -l {} \; | grep lang3/SystemProperties

Первая команда показывает цепочку, по которой зависимость попала в указанную конфигурацию, и там будет flink-connector-jdbc-core. Вторая находит jar в кэше Gradle и показывает в нём класс SystemProperties из чужого пакета.

Первая мысль это исключить jar из тестовых зависимостей. Она не работает, потому что он нужен самому коннектору.

NoClassDefFoundError: io/openlineage/sql/OpenLineageSql

Рабочее решение в том, чтобы поставить настоящую библиотеку раньше на classpath. Для всех задач типа Test мы берём jar commons-lang3 из разрешённых зависимостей и дописываем его в начало. Это строки 76-78 файла сборки из шага 5. Первым найденным классом становится настоящий, а openlineage остаётся на месте и работает.

Похожая ловушка с лишним коннектором была в уроке 14. В Java порядок на classpath решает, какой из одинаковых классов загрузится, поэтому при странном NoSuchMethodError первым делом ищи вторую копию класса.

Шаг 8. CI

Положи в проект .github/workflows/ci.yml.

Блок on запускает файл на каждый push в main и на каждый pull request. Задание build гонит обычные тесты и собирает толстый jar, а upload-artifact сохраняет его как артефакт прогона. Действие setup-gradle настраивает Gradle и его кэш. Флаг --console=plain убирает анимированный прогресс, который только мешает читать лог. Задание e2e благодаря needs: build стартует только после успеха первого. Отдельной настройки Docker в нём нет, расчёт на то, что на раннере Ubuntu от GitHub он уже стоит.
