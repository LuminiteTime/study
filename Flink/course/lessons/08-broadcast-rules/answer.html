Ответ

Константа правила стоит рядом с идентификатором velocity.

Проверка вызывается из processElement до правила частоты. Оба правила получают один и тот же объект настроек, прочитанный из broadcast state один раз.

Сама проверка.

Если в сообщении нет поля blockedCountries, Jackson передаст в конструктор record null, поэтому сначала проверка на null. Состояние с ключом правилу не нужно. Решение зависит только от платежа и настроек, а идентификатор алерта строится из правила и paymentId, так что повторная обработка того же платежа даст тот же алерт. Снять блокировку можно новым сообщением с пустым списком.

Тест присылает правило с DE и подаёт один платёж из DE.

Проверь сборку и стенд. В нашем прогоне весь набор, 25 тестов, прошёл без падений.

./gradlew test shadowJar
docker compose exec jobmanager flink cancel <JobID>
scripts/submit.sh
./gradlew loadgen
echo '{"velocityMaxPayments":1000,"blockedCountries":["PL"]}' | docker compose exec -T kafka \
  /opt/kafka/bin/kafka-console-producer.sh --bootstrap-server localhost:9092 --topic rules.config
docker compose exec -T kafka /opt/kafka/bin/kafka-console-consumer.sh --bootstrap-server localhost:9092 \
  --topic fraud.alerts --from-beginning --timeout-ms 10000 2>/dev/null | grep -c '"ruleId":"blocked-country"'

--timeout-ms завершает чтение, если 10 секунд нет новых записей, а grep -c считает строки с нужным правилом. На нашем стенде за 25 секунд при 100 платежах в секунду пришло 539 алертов blocked-country, задание не перезапускалось. Это около пятой части от 2500 платежей, и так и должно быть, генератор выбирает страну равномерно из пяти.
