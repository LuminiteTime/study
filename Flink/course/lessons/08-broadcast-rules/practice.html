Что будет в конце

Правило velocity из урока 7 переедет в новую функцию DynamicRules, которая берёт порог из топика rules.config. Ты отправишь в топик новое правило консольным продюсером Kafka, и задание применит его без перезапуска. Проверку заблокированных стран ты напишешь в задании, поэтому в практике её код пропускаем. Файлы решения пока создавать не нужно.

Шаг 1. Настройки правил

Создай model/RuleConfig.java. Настройки описывает record с двумя полями, лимитом платежей карты в минуту и списком заблокированных стран.

Слова implements Serializable появились после ошибки. Первая версия была без них. Тесты прошли, jar собрался, а flink run упал ещё до старта задания.

RuleConfig[velocityMaxPayments=10, blockedCountries=[]] is not serializable. The object probably contains or references non serializable fields.

Причина в поле defaults функции DynamicRules. Значения по умолчанию передаются в конструктор и хранятся в поле, а функция уезжает на TaskManager через сериализацию Java вместе со всем, на что ссылаются её поля. В самом broadcast state RuleConfig хранится иначе, через сериализатор Flink для POJO, и Serializable ему не нужен. Record Flink разбирает как POJO, это было в уроке 3.

В исходниках

Проверку запускает метод, который добавляет функцию в граф. Ещё на клиенте он пропускает её через clean окружения.

Метод clean зовёт ClosureCleaner с проверкой сериализуемости, и её текст совпадает с нашей ошибкой. Код проверки и причину, по которой test harness её обходит, мы разберём в уроке 16. Для практики хватит вывода. Забытый Serializable ловит отправка задания или тест, который строит граф, а тест функции на harness его пропускает.

Документация: Data Types & Serialization

В JobConfig добавь имя топика правил. Умолчание rules.config совпадает с топиком, который уже создаёт служба kafka-init.

Шаг 2. Разбор, который не роняет задание

Правила пишет человек, и опечатка в JSON рано или поздно случится. Если схема бросит исключение, задание упадёт целиком. Сейчас чекпоинты выключены, и без них Flink по умолчанию задание не перезапускает. Когда в уроке 11 чекпоинты появятся, перезапуск включится сам, и задание будет раз за разом доходить до той же записи и падать снова. Создай pipeline/LenientJsonSchema.java. На битой записи она пишет предупреждение в лог и возвращает null.

ObjectMapper помечен transient и создаётся в open, один раз на подзадачу. В сериализованную схему он не попадает. Класс записи передаётся конструктору, поэтому схему можно взять для любого типа.

В исходниках

Почему хватает null. Источник Kafka с setValueOnlyDeserializer оборачивает схему и вызывает её вариант с Collector.

Этот вариант по умолчанию отдаёт объект дальше, только если deserialize вернул что-то отличное от null.

Пустой результат просто не попадает в поток, и задание продолжает работать с прежними правилами.

Теперь о том, что было бы без этой схемы. Стратегия перезапуска по умолчанию зависит от того, включены ли чекпоинты. Описание настройки restart-strategy.type говорит об этом прямо.

Документация: Apache Kafka Connector, Restart Strategies

Шаг 3. Watermark для потока правил

Создай pipeline/RuleWatermarks.java. Это стратегия из теории, которая не даёт правилам держать время оператора.

ПРОСТЫМИ СЛОВАМИ

forGenerator собирает стратегию из фабрики генераторов. Источник сам создаст генераторы из этой фабрики.

onEvent пустой. Время правила нас не интересует, по записям watermark не двигаем.

onPeriodicEmit вызывается периодически, по умолчанию раз в 200 мс, это настройка pipeline.auto-watermark-interval. Каждый раз выпускаем Long.MAX_VALUE, обещание, что от этого входа старых данных не будет никогда.

Стратегия типизирована RuleConfig, поэтому подходит прямо в fromSource источника правил.

ПРОСТЫМИ СЛОВАМИ

Платёж проверяется правилом частоты с порогом из текущих настроек. Настройки processElement получил строкой выше из broadcast state через контекст только для чтения.

Шаг 6. Подключи поток правил

В PayGuardJob появляется второй источник и оператор с двумя входами.

Источник правил читает свой топик со своей группой потребителей, к имени группы добавлен суффикс -rules. Значения разбирает LenientJsonSchema, время задаёт RuleWatermarks.neverHoldBack(). Вызов broadcast(DynamicRules.RULES) делает поток широковещательным, а byCard.connect(rules) соединяет его с платежами, разбитыми по карте. Значения по умолчанию берутся из параметров запуска, как раньше лимит VelocityRule.

Источник правил начинает с OffsetsInitializer.earliest(). Чекпоинтов у нас пока нет, и после каждого запуска broadcast state пуст. Чтение топика с начала восстанавливает настройки, а последнее сообщение перезаписывает предыдущие. Kafka хранит порядок только внутри партиции, поэтому с четырьмя партициями «последнее» при повторном чтении может оказаться не тем, что отправили последним. Это ещё один довод за одну партицию в проде.

Шаг 9. Как увидеть застрявшее время

Если хочешь проверить ловушку из теории своими глазами, замени в PayGuardJob вызов RuleWatermarks.neverHoldBack() на WatermarkStrategy.noWatermarks(), собери и перезапусти задание. Мы этот вариант на стенде не запускали, поэтому ниже то, что предсказывает код. Команда с watermarks из шага 7 вернёт для rules-dynamic число -9223372036854775808, это Long.MIN_VALUE, а у deduplicate время будет расти. Не забудь вернуть neverHoldBack.

В исходниках

У задачи с двумя входами на каждый вход свой измеритель watermark, а наружу показывается их минимум.

Измеритель входа начинает с Long.MIN_VALUE и меняется, только когда по входу пришёл watermark. Минимум считается обычным min.

Минимум регистрируется метрикой задачи с именем currentInputWatermark.

Обработчик REST для /watermarks отдаёт именно эту метрику по каждой подзадаче вершины.
