Ответ

Меняем одно поле и следим за ресурсом.

kubectl patch flinkdep payguard --type merge -p '{"spec":{"job":{"parallelism":3}}}'
kubectl get flinkdep payguard -w

--type merge сливает переданный JSON с текущим объектом, остальные поля spec не трогаются. По коду ресурс проходит UPGRADING, DEPLOYED и STABLE, промежуточные значения в выводе -w мелькают быстро. На стенде от patch до RUNNING и STABLE прошло 52 с.

kubectl get flinkstatesnapshots

Появился ресурс payguard-savepoint-upgrade-1794126582605 в состоянии COMPLETED с путём file:/flink-data/savepoints/savepoint-34e016-c18e5dd0fdb1. Первые шесть знаков после savepoint- взяты из jobId старого задания.

В исходниках

Имя каталога savepoint Flink собирает из префикса, начала jobId и случайного хвоста.

По имени каталога всегда видно, из какого задания снят снимок, даже когда ресурсов FlinkStateSnapshot уже нет.

Теперь проверяем новое задание. jobId сменился, перечитываем его и заново открываем port-forward.

kubectl port-forward svc/payguard-rest 18081:8081
JOB=$(kubectl get flinkdep payguard -o jsonpath='{.status.jobStatus.jobId}')
curl -s localhost:18081/jobs/$JOB/checkpoints | jq '{restored: .counts.restored, path: .latest.restored.external_path}'
curl -s localhost:18081/jobs/$JOB | jq '[.vertices[] | {name, parallelism}]'
curl -s localhost:18081/overview | jq '{taskmanagers, "slots-total"}'

Результаты на стенде. checkpoints.restored равен 1, latest.restored.external_path совпадает с путём из FlinkStateSnapshot. Параллелизм всех вершин 3. В /overview стало taskmanagers 2 и slots-total 4. Трём подзадачам каждой вершины нужно три слота, у одного TaskManager их два, и ResourceManager попросил у Kubernetes второй под. Новые поды назывались payguard-taskmanager-3-1 и payguard-taskmanager-3-2. Четвёртый слот простаивает.

Состояние разложилось по трём подзадачам через группы ключей, как в уроке 13. Максимальный параллелизм задания не менялся, поэтому снимок подошёл.

Остаётся счётчик неудачных чекпоинтов. Сразу после апгрейда он вырос на 1. Ищем причину в логе JobManager, его Deployment называется так же, как кластер.

kubectl logs deploy/payguard | grep 'Failed to trigger checkpoint'
Failed to trigger checkpoint for job 3f6791727f93c0f73bd891d57caaec79 since Checkpoint triggering task deduplicate (2/3) of job ... is not being executed at the moment. Aborting checkpoint. Failure reason: Not all required tasks are currently running..

Первый чекпоинт по расписанию сработал, пока подзадачи на новом TaskManager ещё разворачивались. Чекпоинт требует, чтобы работали все подзадачи, и координатор его отменил. Следующие чекпоинты прошли COMPLETED, и счётчик больше не рос. Для алертов из урока 17 это значит, что одиночный неудачный чекпоинт после деплоя норма, тревогу поднимают на серию подряд.

Ручной подбор параллелизма можно отдать автоскейлеру оператора. Он сам меняет параллелизм вершин по метрикам загрузки и выкатывает изменения тем же циклом апгрейда, если кластер не умеет применить их на месте. На нашем стенде автоскейлер не проверялся, это следующий шаг, описание в документации Autoscaler.
