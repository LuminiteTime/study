Что будет в конце

В minikube работают оператор, Kafka на постоянном томе, PostgreSQL, генератор платежей и PayGuard в режиме Application с HA. Задание переживает удаление пода JobManager и рестарт Kafka. Новых классов Java в этом уроке нет, добавляются образ, манифесты Kubernetes и скрипт стенда. Ответ на задание тоже состоит из команд, новых файлов для него создавать не нужно.

Шаг 1. Что поставить

Понадобятся minikube, kubectl и Helm. Minikube запускает однонодовый кластер Kubernetes внутри контейнера Docker. kubectl это клиент API Kubernetes. Helm ставит приложения в Kubernetes готовыми пакетами, они называются чартами. Стенд из Compose можно остановить, памяти он заберёт заметно.

Шаг 2. Образ задания

В режиме Application jar должен лежать в образе. Создай docker/job.Dockerfile.

Базовый образ тот же, что в Compose, поэтому версия Flink совпадает с проверенной. Каталог /opt/flink/usrlib Flink добавляет в classpath задания, об этом шла речь в уроке 2. Путь к jar мы позже укажем в FlinkDeployment.

Шаг 3. Скрипт стенда

Создай scripts/k8s-up.sh. Он поднимает кластер, ставит оператор, создаёт инфраструктуру и загружает образ.

ПРОСТЫМИ СЛОВАМИ

Комментарий предупреждает о ловушке, на которую мы наступили. Размер памяти задаётся только при создании кластера.

minikube start создаёт кластер. --cpus=6 и --memory=9g задают ресурсы узла, --driver=docker велит запустить узел контейнером Docker.

helm repo add регистрирует репозиторий чартов оператора. Адрес содержит версию, поэтому чарт совпадает с релизом 1.16.1.

helm upgrade --install ставит оператор или обновляет уже установленный. webhook.create=false отключает webhook проверки ресурсов, иначе пришлось бы сначала ставить cert-manager для его сертификатов. --wait ждёт готовности подов, --timeout 15m даёт на это пятнадцать минут вместо пяти по умолчанию.

Secret payguard-db хранит пароль PostgreSQL. Связка --dry-run=client -o yaml | kubectl apply -f - превращает «создать» в «создать или обновить», и скрипт можно запускать повторно.

ConfigMap payguard-sql несёт sql/init.sql, PostgreSQL выполнит его при первом старте.

Применяем манифест инфраструктуры, его разберём в следующем шаге.

Собираем jar, без него Dockerfile нечего копировать. --console=plain и -q убирают индикаторы прогресса и лишний вывод.

Собираем образ из docker/job.Dockerfile. Точка в конце задаёт контекст сборки, корень проекта.

У minikube своё хранилище образов внутри узла. minikube image load копирует туда образ, и поды найдут его без реестра.

chmod +x scripts/k8s-up.sh
./scripts/k8s-up.sh

Если minikube у тебя уже запускался раньше, скрипт может сработать не так, как написано. Существующий профиль сохраняет свой размер памяти, и minikube честно об этом пишет, но продолжает запуск со старыми 4 ГиБ.

You cannot change the memory size for an existing minikube cluster. Please first delete the cluster.

Стенд из JobManager на 1600m, TaskManager на 2048m, Kafka, PostgreSQL и оператора в 4 ГиБ не помещается. У нас docker stats показал узел minikube на 3.93GiB из 4GiB, и API Kubernetes перестал отвечать.

Unable to connect to the server: net/http: TLS handshake timeout

Лечение одно. Удали профиль командой minikube delete и запусти скрипт заново.

Вторая ловушка ждёт на первом запуске. Образ оператора скачивается долго, и Helm с таймаутом по умолчанию в пять минут не дождался готовности.

Error: resource not ready ... context deadline exceeded

Оператор при этом поднялся сам через несколько минут, ошибка относилась только к ожиданию. Поэтому в скрипте стоит --timeout 15m.

Шаг 4. Инфраструктура в кластере

Создай k8s/infra.yaml. Здесь Kafka, задание Kubernetes для создания топиков, PostgreSQL и два тома.

Deployment это объект Kubernetes, который держит заданное число одинаковых подов и пересоздаёт их при гибели. Service даёт подам постоянное имя в DNS кластера. Благодаря Service kafka задание обращается к брокеру по адресу kafka:9092, как в Compose, и менять настройки задания не нужно. Самое важное в манифесте это том Kafka.

ПРОСТЫМИ СЛОВАМИ

Комментарий объясняет, зачем всё это. Без тома брокер после рестарта забывает топики и транзакции.

KAFKA_LOG_DIRS переносит журналы брокера в отдельный каталог.

Монтируем в этот каталог том kafka-data.

fsGroup назначает группу файлам тома, чтобы процесс Kafka внутри контейнера мог в него писать.

Том берётся из PersistentVolumeClaim kafka-data, заявки на 5 ГиБ в конце файла. В minikube её выполняет встроенный провайдер дисков на узле.

Стратегия Recreate у Deployment Kafka нужна из-за тома. По умолчанию Kubernetes при одной реплике поднимает новый под раньше, чем гасит старый. На одном узле том ReadWriteOnce смонтируется в оба пода, и два брокера получат один каталог журналов. На разных узлах новый под не сможет смонтировать том, пока его держит старый. Recreate сначала останавливает старый под.

Задание kafka-init это объект Job, он выполняет под до успешного завершения. Пока брокер не готов, команда падает, и restartPolicy: OnFailure с backoffLimit: 20 перезапускают её, пока топики не создадутся. У PostgreSQL тома нет. После рестарта он заново выполнит init.sql и потеряет итоги по продавцам. Справочник продавцов восстановится из того же скрипта, для учебного стенда этого хватает.

Том flink-data общий для JobManager и TaskManager, туда пойдут чекпоинты, savepoint и HA. Режим ReadWriteOnce разрешает монтировать том на одном узле. В minikube узел один, и все поды видят один каталог. На настоящем кластере из нескольких узлов эти каталоги кладут в S3 или другое объектное хранилище.

Шаг 5. Описание задания

Создай k8s/payguard.yaml. Это и есть желаемое состояние, которое оператор будет поддерживать.

Первые строки выбирают образ и версию API Flink. imagePullPolicy: IfNotPresent велит не ходить в реестр, если образ уже есть на узле, у нас его туда положил minikube image load. serviceAccount: flink это учётная запись, которую создал чарт оператора. От её имени JobManager создаёт поды TaskManager и пишет HA ConfigMap. Блок flinkConfiguration заменяет переменную FLINK_PROPERTIES из Compose.

ПРОСТЫМИ СЛОВАМИ

Два слота на TaskManager. При параллелизме 2 хватит одного TaskManager, при 3 понадобится второй.

Состояние в RocksDB, как в уроке 19, и инкрементальные чекпоинты из урока 11.

Чекпоинт каждые 15 секунд и не меньше 10 секунд паузы между ними.

Чекпоинты и savepoint пишутся на общий том /flink-data. Каталог savepoint обязателен для режима savepoint, без него оператору некуда снимать снимок.

RETAIN_ON_CANCELLATION сохраняет последний чекпоинт при отмене задания. Это страховка на случай апгрейда stateless или ручной отмены.

HA через Kubernetes, файлы метаданных в /flink-data/ha.

Стратегия перезапуска с растущей паузой. Подробно о ней в уроке 21.

Репортер Prometheus из урока 17 на порту 9249. Prometheus в этом стенде нет, порт пригодится при подключении мониторинга кластера.

Ключа kubernetes.cluster-id в конфигурации нет. Оператор подставляет его сам из имени ресурса, поэтому все объекты кластера называются с префиксом payguard.

Блок podTemplate общий для подов JobManager и TaskManager. Контейнер обязан называться flink-main-container, по этому имени оператор находит основной контейнер и дополняет его своими настройками. В контейнер передаются три переменные окружения для PostgreSQL, пароль берётся из Secret через secretKeyRef и в манифест не попадает. Том flink-data монтируется в /flink-data. fsGroup: 9999 отдаёт файлы тома группе flink, в официальном образе у неё и у пользователя flink идентификатор 9999.

Блоки jobManager и taskManager задают ресурсы. Память здесь означает весь процесс, ту самую величину process.size, которую мы раскладывали в уроке 19.

В исходниках

Как поле memory из манифеста попадает в конфигурацию Flink. FlinkConfigBuilder записывает его в TOTAL_PROCESS_MEMORY нужного процесса, а CPU в отдельную настройку Kubernetes.

Значит, memory: 2048m у TaskManager даёт taskmanager.memory.process.size 2048m. Раскладка областей будет та же, что в калькуляторе урока 19, а лимит контейнера совпадёт с размером процесса.

Документация: Pod template, Reference

Блок job описывает само задание. jarURI со схемой local:// указывает на файл внутри образа. Главный класс возьмётся из манифеста jar, как в уроке 1. parallelism: 2 и upgradeMode: savepoint мы будем менять и проверять в задании. state: running значит, что задание должно работать. Значение suspended остановило бы его тем способом, который задаёт upgradeMode.

Шаг 6. Запусти задание

kubectl apply -f k8s/payguard.yaml
kubectl get flinkdep payguard

flinkdep это короткое имя типа FlinkDeployment. Когда развёртывание закончится, колонка JOB STATUS покажет RUNNING, а LIFECYCLE STATE покажет STABLE. Именно так было на нашем стенде. Теперь открой доступ к REST JobManager. Native-интеграция создаёт для него Service payguard-rest.

kubectl port-forward svc/payguard-rest 18081:8081

port-forward пробрасывает порт 18081 твоей машины в под за этим Service. Команда работает, пока открыт терминал. Во втором терминале спроси кластер о себе и о задании.

curl -s localhost:18081/overview | jq .
JOB=$(kubectl get flinkdep payguard -o jsonpath='{.status.jobStatus.jobId}')
curl -s localhost:18081/jobs/$JOB/checkpoints/config | jq .state_backend
kubectl get configmaps

jsonpath вытаскивает jobId из статуса ресурса, оператор записал его туда при развёртывании. На стенде получилось следующее.

Что смотрелиРезультат
/overviewtaskmanagers 1, slots-total 2, jobs-running 1, flink-version 2.2.1
Бэкенд состоянияEmbeddedRocksDBStateBackend
Длительность чекпоинта105 мс

Один TaskManager на два слота ровно под параллелизм 2. Его под создал ResourceManager JobManager. Оператор через native-интеграцию создал только Deployment JobManager.

Шаг 7. Генератор внутри кластера

Генератору нужен адрес kafka:9092, который виден только внутри кластера. Запустим его подом из того же образа, jar содержит и задание, и генератор. Создай k8s/loadgen.yaml.

Первая версия манифеста запускала java -cp /opt/flink/usrlib/payguard.jar без второго элемента classpath, и под сразу падал.

java.lang.NoClassDefFoundError: org/slf4j/LoggerFactory

В кластере Flink логгер уже есть, поэтому slf4j в jar задания не попадает. Генератор запускается обычной JVM, без Flink вокруг, и логгера не находит. Лечение в строке command. В classpath добавлен /opt/flink/lib/*, там лежит логгер образа. Команда в манифесте запускается без shell, звёздочку в classpath разворачивает сама JVM.

kubectl apply -f k8s/loadgen.yaml
kubectl logs -f deploy/loadgen

Шаг 8. Убей JobManager

Проверим HA. Native-интеграция ставит подам метки app с именем кластера и component с ролью, по ним и выберем под JobManager.

kubectl delete pod -l app=payguard,component=jobmanager
kubectl get pods -l app=payguard -w

Флаг -w следит за изменениями. Deployment сразу создаст новый под. port-forward держится за конкретный под и после его удаления завершится, запусти его заново. Затем посмотри, откуда задание восстановилось.

curl -s localhost:18081/jobs/$JOB/checkpoints | jq .latest.restored

На стенде задание снова было в RUNNING через 34 с после удаления. jobId остался прежним, 0de8a1877f17c73f80cd4c109fc665d4, а восстановление шло из чекпоинта file:/flink-data/checkpoints/0de8a1877f17c73f80cd4c109fc665d4/chk-10. Оператор в этом не участвовал. Новый JobManager взял jobId из своей конфигурации и нашёл указатель на chk-10 в ConfigMap задания.

Шаг 9. Перезапусти Kafka

Теперь проверим том брокера. Генератор пишет 200 платежей в секунду.

kubectl delete pod -l app=kafka
curl -s localhost:18081/jobs/$JOB/checkpoints | jq .counts
kubectl exec deploy/kafka -- /opt/kafka/bin/kafka-topics.sh --bootstrap-server localhost:9092 --list

Через 90 с задание было в RUNNING, чекпоинты шли дальше. Счётчик completed вырос с 2488 до 2494, failed остался 0. Все топики на месте, включая __transaction_state. Бесконечных рестартов нет.

Шаг 10. Что ещё ломалось

До появления тома у Kafka этот же рестарт закончился плохо. Под Kafka перезапустился во время апгрейда, брокер поднялся пустым, остались только топики payments.raw, payments.confirmations и rules.config, которые клиенты создали автоматически. Задание восстановилось из savepoint и упало на фиксации транзакции.

java.lang.IllegalStateException: Failed to commit KafkaCommittable{producerId=31, epoch=2, transactionalId='payguard-alerts-0-11', producer=null}
Caused by: org.apache.kafka.common.errors.InvalidPidMappingException: The producer attempted to use a producer id which is not currently assigned to its transactional id.

Задание восстанавливалось 17 раз, 11 чекпоинтов закончились FAILED, состояние RESTARTING не прекращалось. Почему коннектор не пропускает эту ошибку и чего стоило восстановление, разберём в уроке 21. Профилактика уже в манифесте, это том kafka-data и стратегия Recreate.

После инцидента minikube пришлось пересоздавать, и это принесло ещё две ошибки. Сначала minikube delete не смог удалить контейнер узла.

docker rm -f -v minikube: context deadline exceeded

Том узла остался, и новый узел поднялся со старыми данными etcd, базы, где Kubernetes хранит свои объекты. Ресурсы вернулись, а образ задания из хранилища узла пропал.

ErrImagePull: pull access denied for payguard-job

Kubernetes не нашёл образ на узле и пошёл за ним в Docker Hub, где такого образа нет. Лечение в повторном minikube image load payguard-job:1.0.0. Запомни правило. После любого пересоздания узла образ загружают заново.
